# Native authoring: reusable UI, Unicode, fonts, and reviewed edits

Research checked 2026-11-25. Scope: additive components and narrowly reusable implementation references, not competing writing products. No dependencies installed, downloaded code executed, services started, or product files modified. GitHub REST returned HTTP 429, so upstream identities below were verified with GitHub commit Atom feeds and actual raw source/build/license files. A version in a build file is not claimed to be a published release. No binary-size, RSS, frame-time, or manuscript benchmark was performed.

## 1. What should Scribodo retain, and is a native text-system bridge preferable to a UI rewrite?

### Takeaway

Keep raylib + Clay and the author-controlled editing/persistence contracts. The highest-value experiment is an **AppKit NSTextView island within the existing window**, not replacing the whole workbench: compare it against the real IME/accessibility/complex-text gaps before investing in a custom full text stack.

### Cited Findings

#### Actual local baseline

- Read `README.md`, `docs/ARCHITECTURE.md`, `docs/AUDIT-005-repository-audit.md`, `Makefile`, `src/ui/{editor,font,input,mac_window}.c`, `src/core/{text_buffer.h,wrap.c,diff.c}`, and `src/app/reviewed_edit_controller.c`. Architecture is source-traced to `69b98abf1ecf86c560b435a209327175c182eab1`; it explicitly distinguishes author authority, buffer vs saved file vs revision, consent, and derived indexes. The platform target is Apple Silicon macOS, and GAP-005 real input/accessibility is not started. [Architecture](../../docs/ARCHITECTURE.md), [README](../../README.md), [audit](../../docs/AUDIT-005-repository-audit.md).
- `src/ui/editor.c` configures stb_textedit with `uint32_t` character type and `int` positions; Scribodo supplies the gap-buffer access, layout, word navigation, grouped undo, and tracked anchors. `src/core/text_buffer.h` stores codepoint indices, **not grapheme indices**: its “every index a valid character boundary” comment does not establish user-perceived-character safety. `src/ui/input.c:49–58` ultimately obtains committed characters with `GetCharPressed()`, with no marked-text/range/geometry interface in that wrapper. [Editor](../../src/ui/editor.c), [buffer](../../src/core/text_buffer.h), [input](../../src/ui/input.c).
- `src/core/wrap.c` sums per-codepoint advances and breaks at `wrap_is_space`, or hard-breaks an overlong word. `src/ui/font.c:18–32` has a fixed glyph coverage set; its own comment says everything outside becomes tofu pending a dynamic cache. Rendering is one codepoint at a time (`sfont_draw`, `sfont_draw_utf8`), not shaped glyph runs. Combining marks getting zero advance in the missing-glyph path is not contextual mark positioning. [Wrapping](../../src/core/wrap.c), [font implementation](../../src/ui/font.c).
- Native integration is already present: the Makefile compiles `.m` with ARC, links Cocoa/CoreGraphics, and compiles GLFW as Objective-C; `src/platform/dialogs_mac.m` exists. `src/ui/mac_window.c` already manipulates an `NSWindow`, explicitly arm64-only for its objc_msgSend struct-return convention. A proper `.m` bridge would not require converting all C sources or introducing Swift. [Build](../../Makefile), [window bridge](../../src/ui/mac_window.c), [native dialogs](../../src/platform/dialogs_mac.m).
- Audit F1/F2/F3 are persistence defects (unsaved-chat guard, revision identity collision, repeated append on retry), not evidence that changing text widgets fixes durability. An editor migration must retain the stronger save/recovery/author-acceptance design rather than conflate platform text editing with storage correctness. [Audit](../../docs/AUDIT-005-repository-audit.md), [architecture §§5,8](../../docs/ARCHITECTURE.md).

#### Rank 1 serious candidate: AppKit NSTextView island, BORROW bridge patterns / INTEGRATE platform API

- **Not a new GitHub-owned engine:** `NSTextView` is Apple's front end to its text system, drawing/managing text, user selection/modification, input management, key binding, and marked text. Apple explicitly offers either subclassing it or implementing `NSTextInputClient` on a custom NSView. Input protocol alone is not an accessibility or rendering implementation. [Apple NSTextView](https://developer.apple.com/documentation/appkit/nstextview), [Apple NSTextInputClient](https://developer.apple.com/documentation/appkit/nstextinputclient).
- **Concrete C/Objective-C exemplar:** [libui-ng/libui-ng](https://github.com/libui-ng/libui-ng), verified HEAD `43ba1ef553c8993a43a67f1ce6e35983a2660d8c`, 2025-03-15 ([history](https://github.com/libui-ng/libui-ng/commits/master)). Actual [`darwin/multilineentry.m`](https://github.com/libui-ng/libui-ng/blob/43ba1ef553c8993a43a67f1ce6e35983a2660d8c/darwin/multilineentry.m) embeds an NSTextView in NSScrollView and exposes opaque C functions/callbacks, UTF-8 conversion, read-only mode, and programmatic change suppression. It explicitly disables rich text/graphics, quote/dash substitution, spell correction, text replacement and smart insert/delete; enables undo. This is a useful narrow pattern for respecting authored bytes, not a provenance engine.
- **License/build:** libui-ng is MIT ([actual license](https://github.com/libui-ng/libui-ng/blob/master/LICENSE.md)); Darwin code is Objective-C, linking objc + Foundation/AppKit ([Darwin build](https://github.com/libui-ng/libui-ng/blob/master/darwin/meson.build)). Whole libui-ng brings its control/event/layout abstraction and Meson build, which Scribodo does not need. Its root build still labels API versioning a TODO, and observed HEAD is older than the other active candidates: **borrow the bridge design, do not import the toolkit**. [Root build](https://github.com/libui-ng/libui-ng/blob/master/meson.build).
- **Incremental dependencies/footprint:** a new first-party `.m` file plus an opaque C header can use already-linked Cocoa; no third-party runtime, model weights, database, browser, or app-managed service is required by this route. AppKit has resident layout/text-storage allocations and may coexist with UTF-32 storage during transition; **RSS, text duplication cost, startup, long-document layout, and energy are unknown**, not zero. macOS system input services are platform behavior, not owned/packaged by the exemplar. [Local Makefile](../../Makefile), [libui native implementation](https://github.com/libui-ng/libui-ng/blob/master/darwin/multilineentry.m).
- **Named integration points:** add e.g. `src/platform/text_view_mac.m/.h`; host view using the NSWindow already used by `src/ui/mac_window.c`; use Clay's editor pane rectangle from `src/ui/layout.c`; keep `Editor`'s public range/save/dirty/anchor interface in `src/ui/editor.c`; preserve `src/core/doc_io.c`, draft controller, revisions and `src/app/reviewed_edit_controller.c`. This is an integration proposal, not a validated drop-in. [Editor](../../src/ui/editor.c), [layout](../../src/ui/layout.c), [review contract](../../src/app/reviewed_edit_controller.c).
- **Migration cost:** medium/high for one editor surface, much lower scope than rewriting all panes. Need UTF-16 NSRange ↔ UTF-32 codepoint ↔ persisted UTF-8-byte maps (including surrogate pairs), incremental replacement events, recursion guards, one undo authority, composition lifecycle, native focus and shortcut routing, scroll/resize/Retina coordinate conversion, read-only rules, and live anchor rebasing. Do **not** round-trip entire strings every frame or maintain two independently editable buffers. AppKit direct edits must traverse the same transaction/dirty/anchor logic as typed edits. [Apple range-based input methods](https://developer.apple.com/documentation/appkit/nstextinputclient), [existing editor contracts](../../src/ui/editor.c).
- **TextKit caution:** Apple's current docs say accessing `.layoutManager` on macOS 12+ can switch a text view into compatibility mode. The old libui exemplar deliberately uses NSLayoutManager. Choose/test a TextKit mode explicitly; don't accidentally claim a TextKit 2 implementation by borrowing this file. [Apple NSTextView overview](https://developer.apple.com/documentation/appkit/nstextview), [libui layout code](https://github.com/libui-ng/libui-ng/blob/master/darwin/multilineentry.m).
- **Better than Scribodo NOW?** Likely best capability/cost direction **if** native mixed-script editing, IME and assistive use are release requirements and the island passes integration gates. Not yet proven lighter in measured RAM/latency, and it does not make the custom surrounding panes accessible. Platform-native text is a strong prior, not an acceptance result. [Open GAP-005](../../README.md#status).

### Inferences

- The high-cost missing behavior is not rectangular pane layout. A wholesale AppKit/SwiftUI/Qt/ImGui shell replacement is unmotivated until the native text-island comparison is measured. Keep custom chrome and preserve design identity.
- A custom NSView implementing NSTextInputClient plus CoreText would retain full drawn appearance but leaves composition state, glyph/run geometry, accessibility, selection, caret movement and bidi integration with Scribodo. That is substantially more integration responsibility than using NSTextView.
- A native text island addresses only its own focusable text area. Buttons, menus, explorer, findings, chat rows and review actions still need accessible roles, names, states and keyboard navigation.
- Keep automatic manuscript-altering substitutions off by default; explicitly inspect newer system Writing Tools integration as another author-initiated proposal boundary. Never treat system-generated replacement as canon or silent manuscript acceptance.

### Gaps

- No real Japanese/Chinese/Korean composition, dead-key, dictation, VoiceOver, native find, focus switching, fullscreen or AppKit-over-OpenGL compositing test was run. Existing scripts inject committed codepoints; that does not test marked text.
- No confirmed island geometry API design or minimum supported macOS deployment version has been agreed. No evidence that TextKit 1 vs 2 is superior for Scribodo's manuscript workload yet.

## 2. Which surgical Unicode and shaping components are worth integrating if the custom text surface stays?

### Takeaway

**libgrapheme is the best first screen for segmentation across existing UTF-32 buffers**, with libunibreak a strong focused alternative. **utf8proc is the better normalization/casefold/property utility**, not a complete layout engine. HarfBuzz is a justified shaping engine only if Scribodo intentionally retains ownership of the hard surrounding text-system work; try CoreText first on this macOS-only target.

### Cited Findings

#### Rank 2: libgrapheme — INTEGRATE selectively if custom navigation/layout remains

- Exact repo: [FRIGN/libgrapheme](https://github.com/FRIGN/libgrapheme). Verified HEAD `bf20d2f7bce13c7d006a9ca442221399753bce9d`, 2025-12-24 (“Bump version to 3.0.0”). Build declares version **3.0.0** and Unicode **17.0.0**; recentness signal is one observed HEAD, not a claim of busy maintenance. [History](https://github.com/FRIGN/libgrapheme/commits/master), [pinned Makefile](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/Makefile).
- **API fit:** C99, `grapheme.h`; UTF-8 and `uint_least32_t` APIs for character/word/sentence/line breaks and case conversion. `grapheme_next_character_break`, `grapheme_next_word_break`, `grapheme_next_line_break` suit `src/ui/editor.c`, `src/core/wrap.c` and UTF-8 token spans in `src/core/diff.c`. Current header also exposes bidi paragraph preprocessing / embedding levels / line reordering: do not describe 3.0 as segmentation-only or assume it needs FriBidi just because old versions did. [Actual header](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/grapheme.h).
- **Build/dependencies:** POSIX Make + C generators + generated lookup tables. Git checkout Makefile has `wget` rules for missing Unicode data; fetch/generation is a **build** concern, not runtime networking. Vendor a pinned release/data set/generated tables for offline reproducible builds. Sources listed include character, line, word, sentence, case, UTF-8, util and bidi; can evaluate only required modules rather than assume all functionality is free. [Actual build](https://github.com/FRIGN/libgrapheme/blob/master/Makefile).
- **License:** ISC for library; Unicode data has its own notice. Preserve both. README claims freestanding runtime and conformance tests; source was inspected, but freestanding claim and its size/speed comparisons were **not independently benchmarked**. README is internally stale: introduction says Unicode 17 while Conformance still says 15. Build version and tests should decide, not stale prose. [License](https://github.com/FRIGN/libgrapheme/blob/master/LICENSE), [README](https://github.com/FRIGN/libgrapheme/blob/master/README), [character implementation](https://github.com/FRIGN/libgrapheme/blob/master/src/character.c).
- **Cost/missing capability:** in-process table-driven C; no daemon/model/service. Actual binary/RSS/latency unknown. Existing gap buffer is noncontiguous, so contiguous-array APIs need bounded paragraph/line copies or a boundary cache; do not cast gap-buffer backing memory as a contiguous manuscript. Previous-boundary navigation needs an index or safe rescanning; breaking only adjacent pairs without state is insufficient. No font fallback, rasterization, IME, accessibility, undo, provenance or normalization API in inspected public header. [Header](https://github.com/FRIGN/libgrapheme/blob/master/grapheme.h), [Scribodo buffer](../../src/core/text_buffer.h).
- **Better NOW?** Yes for concrete scalar-vs-grapheme deletion/caret/selection bugs and whitespace-only breaking, **if** wrapper/conformance tests prove correct and custom renderer remains. Moderate editor surgery, low language/build impedance. It cannot by itself make mixed-script editing correct, and bidi public APIs add another nontrivial layout/selection integration task. [Existing editor](../../src/ui/editor.c), [wrap](../../src/core/wrap.c).

#### Rank 3: utf8proc — INTEGRATE when normalization/properties are actually needed; alternative for graphemes

- Exact repo [JuliaStrings/utf8proc](https://github.com/JuliaStrings/utf8proc). Verified HEAD `f72a4023617e2d879f2ca93086fd02bc7e3149fe`, 2026-10-14. `NEWS.md` explicitly records **2.12.0, 2026-09-25**, Unicode 18 support; CMake declares 2.12.0. This is verified upstream text, not an assumption based on a calendar. [History](https://github.com/JuliaStrings/utf8proc/commits/master), [NEWS](https://github.com/JuliaStrings/utf8proc/blob/f72a4023617e2d879f2ca93086fd02bc7e3149fe/NEWS.md), [build](https://github.com/JuliaStrings/utf8proc/blob/master/CMakeLists.txt).
- **API/deps/license:** C API, compile `utf8proc.c` (includes generated `utf8proc_data.c`) plus header; no Julia runtime dependency. CMake 3.10 or Make; static define UTF8PROC_STATIC supported. MIT library + separate Unicode-data terms in `LICENSE.md`. Runtime dependencies are ordinary C facilities, not ICU/GLib. [Source](https://github.com/JuliaStrings/utf8proc/blob/master/utf8proc.c), [build](https://github.com/JuliaStrings/utf8proc/blob/master/CMakeLists.txt), [license](https://github.com/JuliaStrings/utf8proc/blob/master/LICENSE.md).
- **Direct fit:** `utf8proc_category`, casefold/normalization APIs can replace/centralize bespoke classification in `src/ui/editor.c` and normalization of **derived search keys**, while `utf8proc_grapheme_break_stateful` can compute boundaries over `tb_get` without changing UTF-32 storage. Header requires calling the stateful function in order on all potential breaks; legacy `utf8proc_grapheme_break` lacks newer stateful rules. [Actual header](https://github.com/JuliaStrings/utf8proc/blob/master/utf8proc.h), [editor](../../src/ui/editor.c), [derived recall terms](../../src/core/recall_terms.c).
- **Missing:** header offers grapheme boundaries, not full word/line segmentation or bidi/shaping. `utf8proc_charwidth` is wcwidth-style terminal columns, **not pixel glyph advance** and cannot replace SFont measurement. No IME/accessibility. A supplemental line/word component would be needed if replacing all current heuristics. [API](https://github.com/JuliaStrings/utf8proc/blob/master/utf8proc.h).
- **Maintenance caution:** actual NEWS/history include recent memory-safety, CHARBOUND+COMPOSE regressions and fixes. Good evidence of active care, also reason to pin a known tested version and include adversarial normalization combinations rather than assuming maturity means zero bugs. Tests can download Unicode fixtures when enabled; vendor fixtures if offline build/test is required. [NEWS](https://github.com/JuliaStrings/utf8proc/blob/master/NEWS.md), [build tests](https://github.com/JuliaStrings/utf8proc/blob/master/CMakeLists.txt).
- **Better NOW?** Useful when Scribodo needs proper Unicode categories/folded search or wants one stable grapheme/property utility. If the only immediate goal is word+line+grapheme boundaries, libgrapheme or libunibreak covers more with fewer separate integrations. No measured footprint comparison; no extra process/model. Never normalize original manuscript bytes or source-span identities invisibly. [API](https://github.com/JuliaStrings/utf8proc/blob/master/utf8proc.h), [source identity boundaries](../../docs/ARCHITECTURE.md).

#### Rank 4: libunibreak — INTEGRATE instead of libgrapheme for a focused breaking layer

- Exact repo [adah1972/libunibreak](https://github.com/adah1972/libunibreak). Verified HEAD `9266fa15190eb2017476e6315b5176143a8f80b3`, 2026-11-24. Current README explicitly says Unicode 17 line/word/grapheme support and documents deferred fixups for lookahead rules. Do not repeat older claims that it implements only UAX #14. [History](https://github.com/adah1972/libunibreak/commits/master), [README](https://github.com/adah1972/libunibreak/blob/master/README.md).
- C API handles UTF-8/16/32, including `set_linebreaks_utf32(s,len,lang,brks)` and MUST/ALLOW/NO-BREAK statuses. This is a natural boundary-mask input to `src/core/wrap.c` once the renderer can measure shaped clusters, and word/grapheme modules can improve editor/diff tokenization. [Actual header](https://github.com/adah1972/libunibreak/blob/9266fa15190eb2017476e6315b5176143a8f80b3/src/linebreak.h).
- zlib/libpng-style license plus Unicode-data terms. Build choices include autotools or direct Make; inspected `src/Makefile.gcc` lists C files and `LIBS :=` empty, no C++ source files. No library daemon, model or external Unicode engine required. Binary/RSS/performance unmeasured. [License and build docs](https://github.com/adah1972/libunibreak/blob/master/README.md), [actual build](https://github.com/adah1972/libunibreak/blob/master/src/Makefile.gcc).
- Better now for line-breaking correctness if retaining custom layout. Not a font, shaper, bidi algorithm, native editing or accessibility solution. Choose **one** breaking layer; don't pile utf8proc+libgrapheme+libunibreak into the binary for redundant segmentation without separate demonstrated needs. [API scope](https://github.com/adah1972/libunibreak/blob/master/README.md).

#### Rank 5: HarfBuzz — CONDITIONAL INTEGRATE, otherwise prefer platform CoreText

- Exact repo [harfbuzz/harfbuzz](https://github.com/harfbuzz/harfbuzz). Verified HEAD `4c4ae97002cc46fff10ff40d6b7e0d1d967200dd`, 2026-11-25; inspected Meson declares **15.2.0** (build version, not independently established release date). C-callable engine implemented in C++11, Meson >=0.60; C++ code does not imply obligate full C++ framework or ICU. [History](https://github.com/harfbuzz/harfbuzz/commits/main), [build](https://github.com/harfbuzz/harfbuzz/blob/4c4ae97002cc46fff10ff40d6b7e0d1d967200dd/meson.build).
- Core shaping API is `hb_shape` with hb_buffer/hb_font; default OpenType font functions and bundled Unicode properties allow shaping without FreeType or ICU. CoreText font/shaper backend exists but defaults disabled. Optional FreeType/GLib/GObject/ICU/Graphite/Cairo integrations are choices, not compulsory dependencies. License is **Old MIT**, with different notices in some subdirectories. [CONFIG.md](https://github.com/harfbuzz/harfbuzz/blob/main/CONFIG.md), [actual options](https://github.com/harfbuzz/harfbuzz/blob/main/meson_options.txt), [COPYING](https://github.com/harfbuzz/harfbuzz/blob/main/COPYING).
- **Current upstream matters:** options now include raster/vector/GPU libraries enabled by default, GPU demo auto, subset enabled, utilities/tests enabled, multiple dependency autodetections. Do not import upstream default build and call that a minimal shaper. For a surgical build explicitly disable unrelated optional modules, utilities, demos, docs/introspection, tests in distribution, and library autodetection you do not intend. Build exact option set against the pinned commit. [Actual options](https://github.com/harfbuzz/harfbuzz/blob/4c4ae97002cc46fff10ff40d6b7e0d1d967200dd/meson_options.txt).
- **Direct change cost:** `src/ui/font.c` must consume glyph IDs, cluster maps, advances and offsets, not codepoint→glyph lookup. `wrap.c`, editor hit testing, selection and cursor x coordinates must consume the same shaped runs. Need fallback per run, dynamic glyph cache/rasterization (CoreText, selected HB raster capability, or separately justified rasterizer), bidi ordering, line breaks, invalidation and IME/AX. The current fixed-atlas `sfont_draw` is not a drop-in target for `hb_shape`. [Existing font](../../src/ui/font.c), [wrap](../../src/core/wrap.c), [editor](../../src/ui/editor.c).
- **Footprint:** in-process native shaping, no model/service required. Exact binary size and RSS unknown. CONFIG.md offers MINI/LEAN/TINY profiles but TINY disables threading and multiple features; do not blindly select it because Scribodo has workers. Its quoted KB/percentage savings are upstream claims, not measurements on this app. [Configuration](https://github.com/harfbuzz/harfbuzz/blob/main/CONFIG.md).
- **Better NOW?** Yes when correct complex-script glyph shaping is required **and** a cross-platform/custom-drawn text engine is an intentional ongoing responsibility. For the current Mac-only MVP, CoreText/AppKit has less incremental third-party dependency surface and solves more of the adjacent native concerns; HB alone is not the best first fix. [Local target](../../README.md#architecture), [API/config scope](https://github.com/harfbuzz/harfbuzz/blob/main/CONFIG.md).

#### Additional screen: FriBidi — DEFER / REJECT duplicate bidi dependency now

- [fribidi/fribidi](https://github.com/fribidi/fribidi), observed HEAD `15393e4937aa95bcf865d92143735746aeb654fa`, 2026-10-29, “Bumped version to 1.0.18”; C bidi engine, LGPL-2.1 license. ### Inferences

- Custom-surface sequence: first correct grapheme boundary operations and segmentation; next choose platform shaping/layout vs a complete custom run model. Adding a shaper while leaving per-codepoint hit testing is not correctness.
- Preserve source bytes: normalized/casefolded lookup keys must map back to immutable originals and original spans. U+00E9 and `e` + combining acute can look alike yet have different codepoint/UTF-8 lengths. Do not rewrite originals to make an index convenient.
- Boundary caches must be invalidated with surrounding context, not just the edited scalar: regional-indicator pairs, ZWJ sequences and Indic conjunct behavior are stateful. Paragraph-scoped recomputation is a reasonable first experiment, not a proven complexity/performance guarantee.

### Gaps

- No arm64 static binary-size/RSS comparison among libgrapheme, utf8proc, libunibreak and native APIs. Upstream “smaller/faster” descriptions should not become report conclusions.
- Actual conformance suites, generated-table reproducibility and OS Unicode-version differences were not executed. libgrapheme's stale README Conformance section is a specific reason to validate pinned tests.
- Native CoreText glyph cache/shaping integration was not prototyped; custom font probing/security behavior must be retained or explicitly re-evaluated, not discarded because a new font API exists.

## 3. Should reviewed edits gain a diff dependency, and what should be tried next?

### Takeaway

Keep the existing bounded diff and, more importantly, the exact anchored acceptance protocol. Improve Unicode token boundaries first. No screened diff library clearly beats the existing implementation **now** once build, license, bounded-work behavior and provenance requirements are included.

### Cited Findings

- `src/core/diff.c` already computes a token-based Myers-style diff, compares token hash **and original bytes**, caps edit distance (default 2000) and falls back to showing whole replacement when the cap is exceeded. Trace storage is explicitly documented O(D²). Its tokenizer treats high UTF-8 bytes as word bytes with a small explicit punctuation list; that is a clearer initial improvement target than replacing the entire diff engine. [Actual source](../../src/core/diff.c).
- `src/app/reviewed_edit_controller.c:147–174` verifies document path, editability, anchor and exact current original string, records a before revision, replaces the range once, then records after revision. Failed before history prevents application; failed after history is reported without undoing the applied editor change. This controller must outlive any diff widget/algorithm change. [Actual controller](../../src/app/reviewed_edit_controller.c), [architecture §8](../../docs/ARCHITECTURE.md).

### Inferences

#### Ranked recommendation

1. **KEEP** raylib + Clay, current C application/backend/persistence and acceptance boundaries. **BORROW** libui-ng's narrow C↔NSTextView bridge pattern; **INTEGRATE** AppKit only in a controlled editor-island experiment.
2. **INTEGRATE conditionally** libgrapheme for custom editor grapheme/word/line behavior. Prefer libunibreak instead when a breaking-only mask layer better fits the cache/layout design; do not take both automatically.
3. **INTEGRATE conditionally** utf8proc for derived-search folding/categories/normalization, or as the single grapheme/property utility if that is the needed scope. Do not mutate authored originals.
4. **DEFER** HarfBuzz until an explicit decision to own shaped-run layout and native input/accessibility. For Mac-only retained custom drawing, compare CoreText first. Do not use today's expanded HB default feature set as a minimal configuration.
5. **KEEP** bounded first-party diff now; use upstream algorithm references only after demonstrating a real deficiency. **REJECT** wholesale Qt/ImGui/libui/STTextView import for the stated problem and current licensing/build constraints.

#### Recommended next experiment (not executed)

- Build a throwaway NSTextView island inside the current raylib NSWindow, framed by the existing Clay editor pane. Expose only C create/destroy/frame/focus, selected range, replace range and committed-change callbacks; use a separate experiment executable/branch, not a product rewrite.
- Keep UTF-32 buffer/undo/source anchors authoritative initially. Explicitly model marked text as transient, and determine one commit/undo policy rather than accidentally persisting each preedit update. Prototype incremental UTF-16↔UTF-32 mapping and inspect which change callbacks fire during IME.
- Disable automatic replacement/substitution and system content rewriting by default; keep accepted proposals atomic and unsaved until explicit save. Retain document read-only, file conflict, draft and before/after revision semantics.
- Acceptance corpus: decomposed accents; emoji ZWJ/family/skin tone/flags; surrogate-pair characters; Arabic/Hebrew mixed with Latin and numbers; Indic conjuncts; CJK wrap; Japanese/Chinese/Korean marked-text composition, replacement/cancel, reconversion, candidate rectangle at scrolled caret; paste CRLF/BOM policy; dead keys; dictation; VoiceOver cursor/selection; repeated undo/redo across typing and accepted AI edits; focus switching between editor/composer/native menus; Retina resize/fullscreen.
- Compare current vs island with **same manuscripts**: startup, app RSS/peak RSS, typing and selection latency percentiles, scroll/frame stalls, long-paragraph reflow, find, memory after repeated open/close. Report native subsystem overhead separately from existing models/services; do not let multi-GB model memory conceal UI regressions.
- In parallel only if custom surface is retained, add a tiny segmentation adapter test harness with pinned Unicode conformance data, test across the gap and near edits, and improve `diff.c` token boundaries without touching proposal acceptance. Promote the best result only after source-offset and history tests pass.

### Gaps

- No candidate performance numbers are measured here. All runtime-cost rankings refer to incremental dependency/integration responsibility, not demonstrated RSS or speed.
- No diff-library swap is justified by a reproduced current algorithm defect or benchmark in this research. Existing O(D²) trace storage may warrant a benchmark at the cap, but is already bounded; lack of minimal diff at the cap is disclosed whole-replacement behavior, not silent manuscript corruption.
- No new UI component remedies audit F1/F2/F3; those need separate authorized fixes. A bridge that bypasses the before-revision/exact-anchor rules would be a regression even if its IME works perfectly.
