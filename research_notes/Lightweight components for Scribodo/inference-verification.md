# Lightweight inference, constraints, verification and testing components

## 1. What should Scribodo keep or consolidate in local inference transport and supervision?

### Takeaway

**Keep llama.cpp; triage/update its security pin first. Keep Scribodo's native supervisor and model policy. Trial consolidation onto the already-linked system libcurl only behind transport-contract tests.** There is no demonstrated reason to replace the working inference stack with an application framework or a new serving runtime.

Simply copying remote.c's easy handle + progress callback is not equivalent to http.c's 100 ms poll slices or pre/post-callback hard-deadline checks. A small worker-owned multi-handle loop with bounded waits is a candidate, not a proven implementation. [progress cadence](https://curl.se/libcurl/c/CURLOPT_XFERINFOFUNCTION.html), [existing deadline semantics](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/http.c#L199-L231), [multi API](https://curl.se/libcurl/c/libcurl-multi.html).
- Seam: preserve `http_request` / `http_request_until`, `HttpResult` and `HttpLineFn` from `http.h`; replace the HTTP header/chunk decoder, request formatting and socket connect/send/receive loops inside `http.c`. Share a bounded post-dechunk line/body sink with `remote.c` **without sharing local-vs-remote destination policy**. Keep Unix-only or fixed loopback endpoint admission, API key handling, no redirects, explicit proxy policy, TLS verification for remote, byte/line limits, cancellation and exact timeout/error semantics. `semantic.c` also uses the local transport for Qdrant; do not accidentally allow arbitrary host URLs through this API. [http.h](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/http.h), [fixed local endpoint construction](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/http.c#L291-L355), [remote policy](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/remote.c#L343-L376).

New vendored production dependencies may be zero because libcurl is already linked. No measured net LOC, RSS, wakeup, first-token or throughput benefit exists from this research. In particular a mature library does not automatically imply faster generation. [existing transport](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/http.c), [existing curl sink](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/remote.c#L250-L321).

### Inferences

- Best efficiency is **fewer maintained protocol implementations, not more orchestration packages**. Keep the native child supervisor: libraries cannot own author consent, model pin validation, memory admission or foreground priority.
- Security-first update is higher value than speculative grammar/runtime replacement. Select a candidate SHA by **verified ancestry containing both fixes**, or review narrow backports; build/release ordering alone is insufficient.

## 2. Is another grammar or structured-output component actually incremental?

### Takeaway

**Use llama.cpp's existing `response_format` schema output first.** llguidance is the most plausible *optional server-side* trial if a measured schema/performance limitation emerges. XGrammar is genuinely native C++ but higher-integration-cost here; Python orchestration packages are not lightweight replacements for two existing C request builders.

## 3. What can be reused for verified answers, evaluation and instrumentation without bloating production?

### Takeaway

**Keep the application's bespoke evidence/authority pipeline and existing evaluation harness. Add narrow coverage-guided fuzz targets first; try generic mutation/evaluation tooling only when it reduces maintenance or finds missed defects.** These developer tools can have zero shipping footprint, but cannot confer semantic correctness or replace author judgment.

### Cited Findings

#### KEEP custom verified-answer/provenance machinery

- Current pipeline retrieves lexical/vector candidates, hydrates manuscript units, scores Qwen3 reranker pairs, extracts up to two spans, verifies against exact source text and returns the manuscript's own bytes. Claim/quotation/relation gates operate on bounded supported forms, and receipts are stored separately from history. These rules embody Scribodo's authority model rather than generic JSON validation. [pipeline API](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/answer_pipeline.h), [receipt contract](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/answer_receipt.h), [architecture limitations](file:///Users/ztflynn/Projects/scribodo/docs/ARCHITECTURE.md).
- `rerank.c` uses the model-card prompt, neutralizes content, bounds text/query, verifies `yes` and `no` token identities, scores from `/completion` probabilities and supports both observed response shapes. Upstream now has a rerank endpoint, but its existence does **not** establish parity for this causal Qwen3 prompt/scoring policy. Keep the 248-line adapter unless an explicit score/ranking/template/precision comparison proves an endpoint can replace it. [rerank implementation](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/rerank.c), [upstream endpoint docs](https://github.com/ggml-org/llama.cpp/blob/244640b7f26e2a7301b27a24edc4f7feaf97d52f/tools/server/README.md).
- Tests already cover typographic normalization, exact-byte recovery, false spans, quote/relationship controls, receipt C/Python agreement, held-out manuscript fixtures, request parity, offline replay and mutation controls. Docs explicitly separate mechanical tests from model quality and human judgment. A generic RAG framework would retain nearly all these obligations while changing source/receipt semantics. [pure pipeline tests](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/tests/test_answer_pipeline.c), [testing inventory](file:///Users/ztflynn/Projects/scribodo/docs/TESTING.md).
- Important limitation to preserve visibly: checks run after streaming; unsupported provisional prose can already have been displayed. Claim extraction itself is a model call; unavailable verdict does not automatically withhold, and passing bounded anchor/relation checks is not proof of truth. Do not describe the product as “verified correct answers.” [architecture §7D](file:///Users/ztflynn/Projects/scribodo/docs/ARCHITECTURE.md), [gate/receipt verdict contract](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/answer_receipt.h).

### Inferences

#### Ranked decisions and staged, test-gated trials

1. **Keep/update llama.cpp + keep native supervision and verified-answer pipeline.** First map the two CVEs to reachable inputs, inspect fixes, select a reviewed fix-containing pin/backport and regenerate dependency evidence. Then run model identity, BF16/F32 kernel census (`-fa off`), tokenizer/template/reference-distribution gates, reranker parity, actual schema requests, private socket/auth, stale-socket, restart/crash/cancellation tests. Keep tool/MCP/agent features disabled. No claim of a safe upgrade before these pass.
2. **Integrate libFuzzer dev-only** on one or two pure APIs first. Establish ASan/UBSan builds, seed corpus and invariant oracles; record coverage and minimize/replay any finding. This adds no new production language or service and attacks the most error-prone byte/parser boundaries.
3. **Trial libcurl behind unchanged local transport API**, with no automatic remote fallback. Compare byte-for-byte callback outcomes/status/errors, pathological server behavior, idle cancellation latency, hard deadline cutoff, caps, concurrency and process shutdown. Benchmark first-token latency, token-gap p95/p99, CPU wakeups, RSS and binary size on the target Mac. Merge only if maintained code shrinks and policy/latency do not regress; otherwise keep the existing small POSIX transport plus fuzzing.
4. **Trial llguidance only on demonstrated need**, using actual llama-integrated revision before any pin change. Compare default grammar vs backend on the exact span/claim/observer schemas, tokenizer/control-token behavior, truncation, unsupported schemas, cold/warm compilation, RSS and whole-turn latency. Ship neither Python Guidance nor a second constraint service.
5. **Optional Mull pilot** on bounded headless gate/receipt functions; measure extra valid mutants killed versus existing domain mutation suites and toolchain upkeep. Keep hand-written authorization bypass mutants and existing audit regressions.
6. **Defer XGrammar, MLX server switch and Promptfoo adoption** until an unmet requirement or measured advantage justifies their integration. Reject Python Outlines/Instructor/Guardrails/Guidance as production dependencies for this C app; borrow schema/retry/eval design lessons without changing provenance or authority.

These stages are recommendations inferred from the implementation and upstream contracts above, not performed experiments. They intentionally do not require model replacement, quantization, a workflow framework or a competitor writing application.
