# Retrieval, indexing, fusion and exact-source selection

Research checked 2026-11-25; read-only inspection, no installations, builds, service launches, or model runs. **Ranked conclusion: keep the existing authorization/hydration pipeline and Qdrant as control; benchmark an exact embedded index first; sqlite-vec is the best minimal-C integration candidate, released USearch the best native ANN challenger, SQLite-Vector a credible exact-scan challenger with a filtering caveat. Fix lexical candidate generation before expecting a vector-index swap to fix quality.** Recommendations below are engineering inferences, not measured improvements.

## 1. What should replace or improve Scribodo's retrieval seams?

### Takeaway

The valuable reusable part is a distance/search engine, not a replacement memory architecture. A small exact index can eliminate Qdrant's separate process and HTTP boundary, but cannot eliminate the embedding/reranking model processes, SQL eligibility rules, exact saved-revision checks, or source verification.

### Cited Findings

- Scribodo explicitly separates retention, selection, and faithful use; author-approved canon is authoritative, generated summaries are not. Consent remains per conversation and canon does not widen it. The newer architecture qualifies the older “selection solved” wording with bounded coverage and remaining quality gaps. Sources: [contract](../../docs/MEMORY-015-effective-memory-contract.md), [architecture](../../docs/ARCHITECTURE.md); immutable upstream [contract](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/MEMORY-015-effective-memory-contract.md), [architecture](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/ARCHITECTURE.md).
- Current planner uses locator-only candidate fusion, then SQL hydration and `unit_valid()`, with final identity/source revalidation. `memory_scope_same()` compares database/project/conversation/tokenizer/history epoch/policy epoch/generation. `document_excerpts()` selects contiguous original-byte windows, preserving nearby dialogue rather than generating a summary. These are assets to keep, not work a vector library replaces. [context_planner.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/context_planner.c).
- Direct seams: implement the existing `memory_vectors_*` interface currently in `semantic.c`, preserving `MemoryCandidate` locator shape; retain `memory_candidate_hydrate[_with_documents]`, outbox claim/ack/fence/generation protocols in SQL. Also account for the **separate legacy observer/canon semantic index**, not just consent-scoped memory, before removing Qdrant. [memory_vectors.h](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/memory_vectors.h), [semantic.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/semantic.c), [memory_store.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_store.c), [document store](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_document_store.c).
- Current Qdrant memory path fingerprints embedding configuration, segregates collection identity by database/project/model fingerprint/generation, filters scope plus allowed attached revision branches and message cutoff **in the vector request**, and rejects malformed/wrong-scope/conflicting locators as a whole. SQL still decides authority. Preserve all of that in a replacement; globally retrieving top-k and then discarding unauthorized hits is not equivalent. [semantic.c, especially mv_path/mv_filter/mv_sources_filter/memory_vectors_search_with_documents_before](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/semantic.c).
- Normal context planning and the verified-answer pipeline differ: the latter gathers up to 32 lexical and 32 vector candidates, keeps SQL-hydrated manuscript units, reranks, selects up to two, extracts spans and returns verified manuscript bytes. Current scope, packet and preparation budgets are part of the comparison, not tunable away to make a new backend win. [architecture §7](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/ARCHITECTURE.md), [answer_pipeline.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/answer_pipeline.c).
- Current lexical fallback is visibly ASCII-limited: `recall_terms()` splits only ASCII punctuation/space, rejects one-byte terms, and folds ASCII only; `recall_match()` performs case-insensitive substring matching, not Unicode word matching. This is a concrete source of apostrophe, normalization, name and short-term misses. [recall_terms.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/core/recall_terms.c).
- Native FTS5 supports BM25, phrase/NEAR queries, Unicode61, trigram, external-content indexes, and custom tokenizer/synonym hooks. Unicode61 is explicitly based on Unicode 6.1, not current Unicode; accent handling is configurable, trigram matching has short-pattern limitations, and external-content consistency must be maintained. Its column filters are **not** conversation authorization. [FTS5](https://www.sqlite.org/fts5.html), [tokenizers](https://www.sqlite.org/fts5.html#tokenizers), [external content pitfalls](https://www.sqlite.org/fts5.html#external_content_table_pitfalls), [synonyms](https://www.sqlite.org/fts5.html#synonym_support).
- `utf8proc` is a compact C normalization/casefolding building block, not a coreference or sentence parser. v2.12.0 headers expose normalization, casefold, categories, UTF-8 iteration, grapheme boundaries. MIT code plus bundled Unicode-data notice: preserve both. [header](https://github.com/JuliaStrings/utf8proc/blob/v2.12.0/utf8proc.h), [license](https://github.com/JuliaStrings/utf8proc/blob/v2.12.0/LICENSE.md), [release](https://github.com/JuliaStrings/utf8proc/releases/tag/v2.12.0).
- Existing local Qwen3 embedding F16, 1024 dimensions and BF16 reranker are distinct from LFM3's non-negotiable BF16 generation policy. Changing an index alone changes none of those inference allocations. [README model/dependency policy](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/README.md), [rerank implementation](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/llm/rerank.c).

### Inferences

- **Integrate experimentally:** FTS5 plus exact vectors as a **derived sidecar**, even if MariaDB remains authoritative. This is retrieval-only, not a recommendation to migrate primary storage. Sidecar inconsistency is handled by existing SQL generation/outbox fences and rebuild, never by trusting cached text.
- Prefer one C-facing adapter returning only `(unit_id, text_hash, source kind/id, scope/generation, score)`; no vector payload text may enter the prompt. Keep embedding model hash + dimensions + metric + normalization + tokenizer/chunker version in an explicit index manifest. Different manifests never share a search space.
- For exact search, materialize a bounded SQL-authorized allowed-ID set/snapshot before scoring and apply that set during scoring/top-k. A sqlite-vec `rowid IN (...)`/metadata path needs tested planner support; an unproven external SQL join after a virtual-table KNN cutoff is not acceptable. With complex eligibility, scanning an explicitly eligible vector relation and scalar cosine distance is the clearest correctness oracle, even if not the fastest.
- An immutable per-query allowed-ID set avoids performing SQL or taking long locks inside native ANN callbacks. Source authorization must be rechecked at dispatch because consent or saved attachments can change while a search runs.
- **Borrow/inspiration:** FTS tokenizer synonyms for author-approved aliases; Unicode-normalized search shadows; sentence/paragraph adjacency for named-person/pronoun chains. These aids may nominate existing source units but cannot rewrite originals, synthesize canon, or authorize neighboring unattached revisions. Normalize a separate search representation and map selected spans back to exact original bytes.
- **Keep** native RRF and reranker protocol. `context_planner.c` already deduplicates per-channel credits and uses a deliberately tuned small-list fusion constant; replacing it with a framework's conventional RRF constant is regression risk. Tune per-channel candidate budgets and rerank candidate coverage, not just the final scoring library.
- No inspected lightweight library resolves cross-chapter pronoun/coreference, implied intent, narrative irony, or canon-vs-speculation use. Reranking cannot rescue an answer absent from its candidates; an exact index only removes ANN approximation, not embedding semantic misses. Generated query expansions should remain derived, audited, bounded and consent-constrained.

### Gaps

- No measured Scribodo latency/RAM win from any replacement. No claim that its current 1024-dimensional embedding model or BF16 reranker is inferior; changing either would need a separate frozen-quality study.
- FTS5/utf8proc would improve defined matching behavior, not prove end-to-end retrieval gains or general multilingual support. No lightweight C coreference engine was source-validated in this pass.
- Full pipeline fusion/extraction quality remains a host/model issue; no new learned-reranking runtime is recommended.

## 2. Which upstreams are actually mature and compatible?

### Takeaway

Nine repositories screened, four search engines deeply inspected at source/build/license level (sqlite-vec, released USearch, SQLite-Vector, Qdrant), plus source/build screening of hnswlib, Faiss and Vectorlite. The best choice is conditional on workload measurements and on the distinction between release and main-branch code.

**1 — sqlite-vec (best minimal-C exact-index candidate).**

- Source is pure C; Makefile has static/loadable targets and Apple-M1 NEON flags. Float32, int8, binary vectors and `vec0` virtual tables; release documentation uses `embedding MATCH ? AND k=?`, metadata and partition constraints. MIT OR Apache-2.0 licensing, no Faiss or Python runtime dependency for C integration. [README](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/README.md), [Makefile](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/Makefile), [MIT](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/LICENSE-MIT), [Apache](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/LICENSE-APACHE).
- Metadata predicates participate in KNN; partition equality prefilters vectors. Limits: 16 metadata columns, four partition keys; docs warn against oversharding and suggest hundreds of vectors per key. Auxiliary columns are not filterable metadata. Thus do not assign a partition key to every tiny chat/revision without measurement. [vec0 metadata docs](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/site/features/vec0.md).
- **Important 2026 correction:** checked main has FLAT index default, `SQLITE_VEC_EXPERIMENTAL_IVF_ENABLE` default 0, plus DiskANN/IVF/rescore files. Saying “sqlite-vec never supports ANN” is now inaccurate; saying its experimental ANN is mature is equally unjustified. Stick to tested release exact functionality. [source](https://github.com/asg017/sqlite-vec/blob/04d28bd21773981e2d266bbf6aa4efbd011eb4f6/sqlite-vec.c), [repository tree](https://github.com/asg017/sqlite-vec/tree/04d28bd21773981e2d266bbf6aa4efbd011eb4f6).
- Incremental footprint: SQLite library + C extension, no added service; SQLite is an added derived store if MariaDB retained. SQLite supports many readers but one writer per DB; serialize ingestion/rebuild writes and use worker-owned connections. No independent durability promise is inferred for extension shadow tables. [SQLite concurrency](https://www.sqlite.org/whentouse.html#high_concurrency).
- Migration inference: moderate adapter/outbox/schema work; potentially much less operational machinery, but not “drop-in.” Delete rows transactionally; abandon incompatible generation tables wholesale; regenerate from SQL. Keep current corruption/lost-index/reseed tests.

**2 — released USearch v2.26.6 (best C-facing ANN challenger).**

- Stable-tag header provides `usearch_init`, `usearch_add`, `usearch_search`, `usearch_filtered_search(callback,state)`, `usearch_remove`, save/load/view, metadata and `usearch_exact_search`. Keys are compact IDs, not Scribodo provenance. A C11 caller can link the native C facade without adopting Python/Rust. [C header](https://github.com/unum-cloud/usearch/blob/v2.26.6/c/usearch.h).
- Build defaults: OpenMP OFF, NumKong accelerated metrics OFF, jemalloc OFF; C library opt-in via `USEARCH_BUILD_LIB_C`. Threads required; NumKong submodule exists but acceleration is optional. Disable unrelated language/tests/benchmarks explicitly and pin every actually enabled sibling. Root Apache-2.0. [stable CMake](https://github.com/unum-cloud/usearch/blob/v2.26.6/CMakeLists.txt), [.gitmodules](https://github.com/unum-cloud/usearch/blob/v2.26.6/.gitmodules), [license](https://github.com/unum-cloud/usearch/blob/v2.26.6/LICENSE).
- Filter callback is part of traversal, not post-top-k filtering. `usearch_exact_search` is a batch exact API; supply already eligible vectors rather than pretending it accepts the ANN predicate. Stable source reserves per-thread scratch and has lookup/free-key mutexes; do not extrapolate blanket race safety to resize, save, reload, remove, and swap. [stable header](https://github.com/unum-cloud/usearch/blob/v2.26.6/c/usearch.h), [index implementation](https://github.com/unum-cloud/usearch/blob/v2.26.6/include/usearch/index_dense.hpp).
- **Main is not stable v2**: checked main CMake declares 3.0.0 and C++20-era machinery; new C guide introduces executors, arenas, dense verbs, broader GPU/NVMe engines and new admission predicates. Do not recommend old `c/usearch.h` against main (it returns 404) or advertise main's concurrency contract as a verified v2 guarantee. [main build](https://github.com/unum-cloud/usearch/blob/840374af1a1dd5d411826bc62fdfe5ef6e41e1de/CMakeLists.txt), [new C guide](https://github.com/unum-cloud/usearch/blob/840374af1a1dd5d411826bc62fdfe5ef6e41e1de/c/README.md).
- Migration inference: moderate/high. Host owns key→immutable locator map, manifest, checkpoint staging/atomic publish, crash recovery and rebuild schedule. Use `multi=false` or enforce one entry per unit; delete cannot revoke authorization by itself. Start with serial mutations and immutable reader generations, then relax only with pinned-version stress tests. ANN graph tombstones/churn require measured rebuild policy.

**3 — SQLite-Vector 1.2.0 (credible released exact-scan alternative).**

- C extension works over ordinary table BLOBs, initialized with `vector_init(table,column,options)`; `vector_full_scan(table,column,query,k)` scores exact FLOAT32, separate quantized scans/preload are optional. Makefile compiles `src/*.c`; tests link SQLite, math, pthread. Root Apache-2.0. [source](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/src/sqlite-vector.c), [Makefile](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/Makefile), [license](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/LICENSE.md).
- **Filtering trap verified in source:** `vFullScanBestIndex()` consumes the table, column, query and optional k constraints; four arguments request internal top-k. Three arguments request an unsorted streaming scan. Therefore an outer eligibility join after the four-argument top-k loses eligible candidates. Three-argument scan + eligibility join + outer distance ordering/limit is correctness-compatible if query plan verified, but still scans the source relation. A per-generation eligible table is another option. [source lines 2692–2945](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/src/sqlite-vector.c#L2692-L2945).
- Upstream publishes exact/quantized benchmark tables, with hardware, vector count and dimensions and warnings distinguishing raw-vector size from RSS. These are **not Scribodo benchmarks** and not evidence of end-to-end BF16 pipeline speed. Quantized 2/3/4-bit scans and recall tradeoffs are irrelevant to a first exact baseline. [README benchmarks](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/README.md).
- Source includes `fp16/fp16.h` and bundled SQLite in test builds: root Apache license is not a complete third-party inventory. FP16 notice location was not successfully resolved in this pass; license audit is a prerequisite, not a hidden assumption of zero transitive licensing. [source includes](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/src/sqlite-vector.c), [bundled FP16 header](https://github.com/sqliteai/sqlite-vector/blob/1.2.0/libs/fp16/fp16.h).
- Migration inference: moderate; ordinary table storage simplifies generation maps, but connection-specific `vector_init` and preload/cache invalidation need tests. Use non-preloaded FLOAT32 first to avoid another stale-cache protocol.

**4 — Qdrant (keep; tune before paying migration costs).**

- Current project 1.20.0 pin is slightly behind checked upstream 1.20.2, not evidence of broken maintenance. Apache-2.0 root, Rust server and substantial dependency graph; remains a separate local process when used as today. [Scribodo pin](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/README.md), [upstream Cargo](https://github.com/qdrant/qdrant/blob/23065a0bf6857c3e5da45f6c8939cc746cc0580e/Cargo.toml), [license](https://github.com/qdrant/qdrant/blob/23065a0bf6857c3e5da45f6c8939cc746cc0580e/LICENSE).
- Payload indexes support cardinality estimation for choosing search strategy and consume extra memory. Filter-aware HNSW benefits from payload indexes created **before** graph construction; adding them later can require HNSW rebuild. So inspect current actual collection/index settings and cardinality before blaming ANN as a category. Qdrant already supports exact search controls as well as HNSW. [indexing docs](https://qdrant.tech/documentation/concepts/indexing/), [search documentation](https://qdrant.tech/documentation/concepts/search/).
- Current docs also describe BM25 text scoring available since 1.20.0 and Qdrant Edge navigation. This pass did **not** source-audit Edge's C embedding/distribution or permissions story; do not treat it as a verified native-C alternative or assume old “Qdrant is only a server” generalizations. There is no need to move source text into a vector payload just because modern Qdrant can rank text. [indexing/BM25 docs](https://qdrant.tech/documentation/concepts/indexing/).
- Migration inference: keeping Qdrant is lowest cost and retains existing recovery/concurrency behavior. Test exact request mode and relevant payload indexes as controls. HTTP serialization, collection management and service supervisor remain overhead, but their RAM/latency has not been measured here.

**Other screened alternatives / why not first.**

- **hnswlib:** header-only C++11, Apache-2.0, no mandatory nonstandard runtime library; requires a small owned C facade. `BaseFilterFunctor`, `markDelete`, reusable deleted slots, save/load. README says query/query safe, insertion/insertion safe, insertion/query not safe; resize not safe with either. Host locking/snapshot swaps required. Current RC adds status/no-exception APIs, but pin stable or explicitly accept RC risk. Good simple ANN reference, not a durable DB or C API out of the box. [README](https://github.com/nmslib/hnswlib/blob/ca426729609b3221563047ceb269cc1213e0d376/README.md), [source](https://github.com/nmslib/hnswlib/blob/ca426729609b3221563047ceb269cc1213e0d376/hnswlib/hnswalg.h), [license](https://github.com/nmslib/hnswlib/blob/ca426729609b3221563047ceb269cc1213e0d376/LICENSE).
- **Faiss:** mature exact/ANN toolbox with optional C API (`FAISS_ENABLE_C_API` default OFF). Current 1.16-era build even has Apple-Silicon Metal backend options; obsolete “no Mac GPU” claims should not be copied. Build has GPU/Python/MKL/extras options enabled by default; a CPU-only C subset must disable unused backends and inspect BLAS/OpenMP dependencies. Root MIT, but CMake has NVIDIA Apache notices; optional backends have their own licenses. For manuscript-scale exact search this is more configuration than sqlite-vec/USearch. [CMake](https://github.com/facebookresearch/faiss/blob/1bafdcc9658be66274efaf229d009f339363bf67/CMakeLists.txt), [C API](https://github.com/facebookresearch/faiss/blob/1bafdcc9658be66274efaf229d009f339363bf67/c_api/Index_c.h), [license](https://github.com/facebookresearch/faiss/blob/1bafdcc9658be66274efaf229d009f339363bf67/LICENSE). Full index-specific filtering/deletion compatibility not audited; do not assume one generic `remove_ids` promise covers HNSW.
- **Vectorlite:** real current activity Nov 25, **not abandoned merely because releases are old**. Current README describes Apple-Silicon support, rowid filter pushdown into HNSW, atomic versioned saves, experimental SQLite-backed DiskANN; current build describes Rust extension plus native hnswlib and Highway, vcpkg bootstrapping may fetch dependencies. That differs materially from the 2024 release commonly recommended online. Apache-2.0 project; hnswlib/Highway require retained notices and Rust dependency audit. Too much release/main uncertainty for “mature lightweight drop-in” recommendation today. [README](https://github.com/1yefuwang1/vectorlite/blob/39a9669f9935a5f730021afd096fb0994585d8db/README.md), [CMake](https://github.com/1yefuwang1/vectorlite/blob/39a9669f9935a5f730021afd096fb0994585d8db/CMakeLists.txt), [manifest](https://github.com/1yefuwang1/vectorlite/blob/39a9669f9935a5f730021afd096fb0994585d8db/vcpkg.json).
- **sqlite-vss:** author explicitly says not in active development; recommends sqlite-vec. Faiss-backed, requires vector0 extension, README says additional filtering on KNN unsupported. Do not choose simply because “SQLite extension” sounds lightweight. Not GitHub-archived, which is a different claim. [README](https://github.com/asg017/sqlite-vss/blob/8d3c6ff2fca651104563779a0d927ea4fba40347/README.md).

### Inferences

- Ranked experimental order: **(1) existing Qdrant exact vs ANN controls; (2) sqlite-vec exact plus FTS5 lexical sidecar; (3) released USearch exact/filtered ANN; (4) SQLite-Vector FLOAT32 streaming exact**. Keep Qdrant if exact embedding/model/reranking time dwarfs index overhead or replacement recovery work outweighs measured savings.
- No vector DB is mandatory. An in-process contiguous FLOAT32 array over eligible units plus a bounded heap is a valid baseline; a library earns adoption by beating that baseline on maintenance/correctness or measured cost.
- sqlite-vec is the cleanest C11 dependency fit; USearch provides the strongest released C API for a custom workbench without a service; hnswlib is an alternative if C++11 simplicity outweighs owning a facade/locking. None manages consent, canonical status or exact manuscript authority.
- Reject large Python RAG frameworks for this seam: they add runtime/orchestration without replacing Scribodo's source contract. No framework was exhaustively audited here and no unmeasured RAM comparison is claimed.

### Gaps

- No full SBOM/transitive license closure for enabled USearch acceleration, Qdrant Rust crates, SQLite-Vector FP16, Vectorlite Rust/Highway stack, or Faiss backends. Root license compatibility is not distribution clearance.
- GitHub release-page timestamps are observed published times; older releases occasionally display multiple asset/tag times. Stable release commit SHAs were not independently resolved for every tag; checked HEAD SHAs must not be mislabeled as the stable release commit.
- No build verified on this Mac, no malformed checkpoint fuzzing, deletion soak or ThreadSanitizer run for these candidates. No release guarantees inferred from star counts or benchmark marketing.
- SQLite itself was treated as a mature platform capability, not an additional pinned repository candidate. Primary SQL migration belongs to the storage review.

## 3. What falsifiable experiment chooses exact vs ANN without hiding quality limits?

### Takeaway

Freeze originals, allowed scopes and embeddings; compare eligibility-first exact ground truth against each ANN index. Report candidate reach and faithful use separately, and separately measure index-only costs, retrieval/model costs and whole-app process costs.

### Cited Findings

- Scribodo already has public-domain novel tooling: `tools/manuscript_import.py` strips Gutenberg wrappers and makes chapter files; `tools/observer_yardstick.py` identifies three untracked Gutenberg novels and refuses missing fixtures unless explicitly skipped. Do not pretend those untracked novels were read in this session. [importer](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/tools/manuscript_import.py), [yardstick](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/tools/observer_yardstick.py).
- Existing reach contract calls for a realistic manuscript fixture, stated facts, revisions, retracted canon and protected ambiguities, with reach independent of faithful use; host latency and token budgets both matter. [MEMORY-015](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/MEMORY-015-effective-memory-contract.md), [MEMORY-017](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/MEMORY-017-reach-harness.md).

### Inferences

Proposed preregistration (not results):

1. **Fixtures:** use the existing Gutenberg corpus named by the yardstick, checksum every imported novel/chapter. Fix importer/chunker/tokenizer/model hashes, attach exact saved revisions. Separate development and held-out chapters/books. Add deterministic revision/consent/history fixtures to those originals rather than quietly modifying gold answers. Public-domain status is jurisdiction-specific; do not redistribute unreviewed editions.
2. **Eligibility oracle:** freeze SQL snapshot and derive authorized IDs for one consented conversation + exact currently attached saved revisions. Include disabled/archived other chats, changed/deleted/detached files, old/new revisions, stale generations and different model namespaces as negatives. Vary eligible fraction (e.g. 100%, 10%, 1%) and corpus history growth independently. These percentages are experiment parameters, not real workload claims.
3. **Baseline engines:** current production Qdrant; same Qdrant with exact search enabled; direct eligible-array FLOAT32 exact; sqlite-vec release exact; USearch v2.26.6 exact and filtered ANN; SQLite-Vector optional. Use identical vectors, dimensions, metric, normalization and deterministic tie-breaking. Do not compare a 384-dimensional quantized candidate to current 1024-dimensional floats and call the difference “index overhead.”
4. **Measure two retrieval stages:** ANN recall@k against eligible exact-neighbor oracle (algorithm approximation); answer-bearing source recall@16/32/64 and after fusion/rerank/packet fitting (semantic/task reach). Exact-neighbor agreement is not answer recall. For gold multi-hop facts score whether all needed spans arrive. Keep returned-unit IDs and SQL-hydrated exact bytes auditable.
5. **Lexical ablations:** current SQL lexical/fallback; FTS5 Unicode61 with declared accent behavior; trigram fallback for substring/name variants; utf8proc normalization shadows; optional explicit aliases/adjacent paragraphs. Label name/diacritic/composed-vs-decomposed, curly apostrophe, one-character names, pronoun-only dialogue, cross-paragraph referents, paraphrase, negation, timeline and conflicting revisions. Candidate expansion uses only authorized source neighborhoods.
6. **Fusion/rerank:** freeze current RRF first, vary only index. Then independently ablate lexical changes, channel limits, RRF constant and Qwen reranking. Keep full-query reranking as control; split-question/expanded-query variants must not increase eligibility. Evaluate sources lost before reranking, sources reranked out and sources clipped by the final two-unit span budget separately.
7. **Faithful use:** for a fixed oracle evidence packet, run pinned LFM3 BF16 and current BF16 reranker without weight-policy changes. Score quotations/source identity, canon authority, ambiguity, wrong-person pronouns, superseded facts and unsupported assertions. Then run ordinary retrieved evidence. Never combine faithful-use score with reach into one headline mean.
8. **Cost accounting:** warm/cold p50/p95/p99 search and end-to-end preparation; source hydration time; embedding time separately; reranking per candidate/batch separately; final extraction/generation separately. Measure app RSS, index-service RSS, each model-server RSS, and whole-machine pressure/swap, not only serialized index bytes. Record idle/service-start time, on-disk size, outbox drain, rebuild time and UI deadline misses. Raw vector payload alone is `N * 1024 * sizeof(float)` for FLOAT32 (arithmetic, not measured RAM; ignores graph/ID/cache/allocator/model costs).
9. **Churn/concurrency:** append, saved revision replacement, archive/consent revocation, delete/reseed failure, query during rebuild, process death around checkpoint publish and outbox ack. Replay old checkpoints deliberately; ensure stale generation/model maps cannot hydrate into a request. Measure ANN recall decay after churn and cost of tombstone cleanup/full rebuild. Concurrent filtering callback must not read a mutating eligibility container.
10. **Decision rule:** safety violations must be zero; any unauthorized/stale source reaching packet is disqualifying. Keep existing production budget and no held-out reach regression. Prefer exact if it meets p95 preparation budget and has lower measured whole-app idle/runtime cost; permit ANN only if exact violates the preregistered cost budget and ANN demonstrably meets it with acceptable held-out reach. Set acceptable latency/recall deltas before running, not after seeing results. Report per-book/per-category results and uncertainty, not only means.

### Gaps

- Existing local fixtures and private dated model evidence were not executed or revalidated; all proposed cutoffs except existing production budgets require preregistration.
- This research provides no measured “vectors per manuscript,” LOC, index RAM, service RSS or latency. Upstream benchmark numbers were intentionally not transplanted across hardware/models/dimensions.
- Retrieval improvements cannot establish safe use of inferred intent or perfect absence claims. Preserve coverage notices and withholding/source-span behavior even if candidate recall improves.
