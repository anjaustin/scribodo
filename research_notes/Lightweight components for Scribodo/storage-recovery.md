# Structured persistence, revisions, durability and recovery

Research date: **2026-11-25**. Read-only source research; no installs, upstream execution, services, product edits or benchmarks. Scope: storage/recovery, not vector-search comparisons. “Integrate” below is conditional on the stated gate, not approval to migrate.

## 1. Which structured-store components actually simplify the whole system?

### Takeaway

**Rank 1 architectural prototype: upstream SQLite + FTS5, directly through its C API and a small Scribodo-owned adapter. Rank 1 immediate action: keep/harden MariaDB while fixing the reproduced caller-policy defects.** SQLite is a deliberate backend and operational architecture change, not a drop-in replacement for Connector/C. It can remove one database daemon and considerable operational machinery; it cannot remove provenance, author-consent policy, independent manuscript files, or file/DB reconciliation.

### Cited Findings

**Existing seams and non-negotiables**

- Current authority is manuscript files plus the selected structured backend; Qdrant is rebuildable locators, and a marked/offline project deliberately pauses rather than silently creating another file history. Import preserves identities, commits, then publishes a marker; copied and moved projects have different identity rules. Keep these invariants regardless of engine. [Architecture §§4–5, 7](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/ARCHITECTURE.md)
- `src/app/db.c` owns Connector/C connection setup, asynchronous socket/deadline polling, query/result adaptation and migrations. SQL throughout `memory_store.c`, `memory_document_store.c`, `store_records.c` uses `FOR UPDATE`, `ON DUPLICATE KEY`, MariaDB timestamps and joins. Engine replacement therefore reaches actual SQL and locking protocols, not just `db_open()`. [db.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/db.c), [memory_store.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_store.c), [memory_document_store.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_document_store.c)
- The audit’s file-chat failure guard, repeated-successful-retry duplication, and truncated-filename revision collision are application-policy/identity bugs. A DB or Git library does not fix `chat_window_info()` ignoring non-windowed failures, failure acknowledgement tied to DB sequence, or callers choosing colliding keys. [AUDIT-005 F1–F3](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/AUDIT-005-repository-audit.md)

**Top candidate 1 — SQLite core/FTS5: INTEGRATE only after an architectural prototype**

- Exact provenance: [sqlite/sqlite](https://github.com/sqlite/sqlite) is the **official Git mirror** of the SQLite source tree, not the canonical development system. The maintainers’ README points to SQLite.org/Fossil and explains public-domain contribution restrictions. Behavioral documentation and release authority are [sqlite.org](https://sqlite.org/), not an arbitrary amalgamation repo. [Mirror README inspected](https://github.com/sqlite/sqlite/blob/52acf77f59baecccb079a2fa432a7c2d51870ea8/README.md)
- Verified stable pin: **3.54.1, 2026-10-16**, Git tag `version-3.54.1` resolves to **`57520227c95396ce39ba6ecaac8d475b78dd3964`** (`git ls-remote` during this research). Official Fossil `SQLITE_SOURCE_ID`: **`2026-10-16 14:45:20 555e07ef33f69a0957d24d8e555b702464a131d6f1607f4c3c1e4551e8e6ca76`**; official SHA3-256 of `sqlite3.c`: **`e2b869d3003b33c942b7dd7063604fbc53553e1b66609570df39b9b7b558ee81`**. Distinguish Git commit from Fossil source ID; do not substitute one for the other. [Official release history](https://sqlite.org/changes.html), [pinned Git source](https://github.com/sqlite/sqlite/tree/57520227c95396ce39ba6ecaac8d475b78dd3964)
- Language/API/build/license: native C API; `sqlite3.c`/`.h` amalgamation can be compiled into the C11 app, with `SQLITE_ENABLE_FTS5` explicitly set. No server, Rust/Go runtime or SQL client connector required. Core deliverable is public domain; the full development tree contains separately licensed accessories, so do not describe every file in the checkout as public domain. Modern common source builds need compiler/make; tests/accessories can require Tcl. [FTS5 build](https://sqlite.org/fts5.html#compiling_and_using_fts5), [source README and license](https://github.com/sqlite/sqlite/blob/52acf77f59baecccb079a2fa432a7c2d51870ea8/LICENSE.md), [3.48 build change](https://sqlite.org/changes.html#version_3_48_0)
- Concurrency: WAL allows readers alongside a writer, **not multiple simultaneous writers**. Long readers can starve checkpoints, WAL can grow, automatic checkpointing can add latency to the commit that triggers it, and `SQLITE_BUSY` remains possible. WAL requires one host/local filesystem, and attached databases in WAL are not atomically committed as a set. [Official WAL](https://sqlite.org/wal.html)
- Durability: WAL `synchronous=FULL` syncs each committed transaction; `NORMAL` can lose acknowledged transactions on power loss/hard reset. macOS `fullfsync=ON` uses `F_FULLFSYNC`, defaults off; if enabled for all syncs, separate `checkpoint_fullfsync` is redundant. These remain OS/hardware assumptions, not protection against every faulty device. [WAL durability](https://sqlite.org/wal.html#performance_considerations), [PRAGMAs](https://sqlite.org/pragma.html#pragma_fullfsync), [atomic-commit assumptions](https://sqlite.org/atomiccommit.html)
- **Current-release warning:** official docs report the WAL-reset race affecting versions through 3.51.2, fixed in 3.51.3 and later with selected older backports. The implicated pattern is concurrent connections writing/checkpointing—relevant to Scribodo’s worker connections. Do not casually link whichever old SQLite macOS supplies without checking actual version/fix provenance. [Official WAL-reset bug](https://sqlite.org/wal.html#walresetbug)
- FTS5 provides lexical matching, BM25/rank, snippets, Unicode61/Porter/trigram tokenizers. External-content tables can avoid duplicate original text, but **caller triggers/transactions must maintain their consistency**, including initial rebuild. Trigram full-text queries do not match substrings under three Unicode characters; no automatic equivalence to current MariaDB recall behavior. Hydrate exact source bytes from ordinary authoritative rows, not highlighted snippets. [Official FTS5](https://sqlite.org/fts5.html)
- Concrete fit: adapt `db.c/.h`, `store_*.c`, `memory_*store.c`, `recall.c`, `project_store.c`; replace MariaDB branch of `tools/services*.sh`, `tools/backup.sh`, `tools/restore.sh` and `service_supervisor.c`. Potential savings: MariaDB daemon, local DB credentials/port/health/reconnect machinery, Connector/C static-link LGPL distribution work, native-vs-Docker DB migration branch, dump/restore dependency. These are **inferred removal opportunities**, not a measured LOC reduction. Qdrant/model daemons remain unless separately replaced. [Current services and dependencies](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/README.md), [backup.sh](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/tools/backup.sh)

### Inferences

- A realistic minimal C wrapper is **the existing `Db` shape reimplemented around `sqlite3_prepare_v3`, bind/step/reset/finalize**, not a new ORM. Own checked typed arguments/rows, statement lifetime, extended error codes, transaction cleanup, bounded busy/cancel behavior and backup. Keep raw-handle access for FTS/diagnostics. No compelling mature, comprehensive pure-C wrapper was established in this search; do not force a C++ dependency to save a few calls.
- Prototype one local database holding all related authority for the first comparison, preserving existing project IDs. A later per-project `.scribodo/project.sqlite` format can simplify portability, but changes copy/fork ownership rules and cross-project operations; treat it as a second decision, not a free consequence of SQLite. Never imply copying an open `.sqlite` without its WAL is safe.
- Retire the legacy runtime backend only after a supported import/export migration path exists; keeping MariaDB + SQLite + legacy files indefinitely increases rather than reduces the system.

### Gaps

- **Unknown measured footprint:** no comparative RSS/PSS, binary size, cold-start, checkpoint tail latency, backup latency, storage growth or deleted first-party LOC was measured. No claim such as “saves X MB” is justified.
- GitHub API rate limits blocked later release/date lookups for the screened secondary candidates. Their HEAD SHAs were verified with `git ls-remote`; exact commit dates and latest releases were not verified. They are not adoption recommendations.

## 2. What should be reused for revisions, atomic file replacement and backups?

### Takeaway

**Keep SQL immutable revisions and independent plain files; borrow proven durability patterns rather than add Git as a second authority.** SQLite’s online backup API is the strongest actual replacement building block after a DB migration; libarchive is useful only if a portable in-process archive removes enough helper code, and restic belongs outside the core as optional local/offline backup retention.

### Cited Findings

**Top candidate 3 — libgit2: BORROW/INSPIRATION; REJECT as default History backend**

- Maintainer project [libgit2/libgit2](https://github.com/libgit2/libgit2); **v1.9.7, 2026-08-13**, verified tag SHA **`49e408b3208bc3093757a1c2db938d3590f3f412`**. C public API, CMake build; GPLv2 with linking exception, plus bundled-source license notices. System/bundled zlib and regex choices, pthreads and hash implementation; HTTPS/SSH are optional and should be disabled for a local-only build. macOS system crypto/Unicode support is available. [Release](https://github.com/libgit2/libgit2/releases/tag/v1.9.7), [README dependencies](https://github.com/libgit2/libgit2/blob/49e408b3208bc3093757a1c2db938d3590f3f412/README.md), [build](https://github.com/libgit2/libgit2/blob/49e408b3208bc3093757a1c2db938d3590f3f412/CMakeLists.txt), [actual license exception](https://github.com/libgit2/libgit2/blob/49e408b3208bc3093757a1c2db938d3590f3f412/COPYING)

This is a **private internal utility, not a supported standalone public atomic-write library**; it depends on libgit2 utilities. Borrow the sequencing/error-state tests and design, not an isolated uncompilable file or licensing assumptions. [Pinned implementation](https://github.com/libgit2/libgit2/blob/49e408b3208bc3093757a1c2db938d3590f3f412/src/util/filebuf.c)

[Pinned os_unix.c](https://github.com/sqlite/sqlite/blob/57520227c95396ce39ba6ecaac8d475b78dd3964/src/os_unix.c), [official power-loss assumptions](https://sqlite.org/atomiccommit.html)

**Additional screened recovery component**

- [benbjohnson/litestream](https://github.com/benbjohnson/litestream), verified HEAD **`92a93c2b75d381f711091be76cc7bd845397401f`**: **inspiration/defer**. Ben Johnson’s standalone SQLite WAL replication/recovery tool supports local-file replicas as well as remote backends; README marks beta and describes a source `_litestream_lock` table and bounded shutdown. [Pinned README](https://github.com/benbjohnson/litestream/blob/92a93c2b75d381f711091be76cc7bd845397401f/README.md)
- Upstream SQLite already supplies incremental **online backup** (`sqlite3_backup_init/step/finish`) and `VACUUM INTO`; completion gives a consistent database snapshot, not a whole-project snapshot. ### Inferences

- Git is worth a separate prototype only if interoperable Git export/branching or material history compression is a genuine product need. For current linear immutable snapshots, adding object DB/refs/pack/GC plus SQL revision-to-blob mapping and recovery likely adds a third consistency boundary. Git does not replace chat/canon/jobs relations, stable document IDs, explicit author action, or backups on another device.
- Store revision identity independently of pathname and text hash: stable document UUID plus immutable revision UUID; hashes verify/deduplicate bytes, not author authority. A Git blob’s identical text across two documents is not permission to merge histories. Preserve original IDs/source ranges, saved-revision pointer and rename aliases during import.
- Harden the file primitive rather than promise magical atomicity: checked complete writes, exclusive sibling temp, permission policy, full-sync mode where supported, checked close/rename/directory publication, explicit “new bytes visible but durability uncertain” outcome after a post-rename failure, and retained recoverable drafts. Audit every caller before changing success semantics.

### Gaps

- No libarchive or libgit2 minimal ARM64 build/linked dependency report was produced. No compression/dedup break-even measured on Scribodo history. Restic binary RSS/size and incremental bundle dedup effectiveness unknown.
- Real APFS power-loss/drive-cache behavior and metadata preservation (ACLs/xattrs/permissions) require macOS-specific acceptance; SIGKILL recovery tests do not establish power-loss durability.

## 3. Which migration, reconciliation and job invariants must survive, and what falsifies adoption?

### Takeaway

**Keep jobs/outbox in the same authoritative SQL transaction as their source changes; do not add a queue server.** The adoption gate is exact source/authority preservation plus demonstrable removal of a daemon and operational code under realistic contention and crash/recovery—not a synthetic insert benchmark.

### Cited Findings

- Current document ingestion comments and SQL commit unit/receipt cursor/outbox intent together; outbox claim/ack tracks owner, fence, generation, attempts, retry and lease. That machinery expresses authorization and stale-worker rejection, not accidental MariaDB plumbing. [memory_document_store.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_document_store.c), [memory_store.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/memory_store.c)
- SQLite has multiple readers and one writer; `BEGIN IMMEDIATE` acquires the write transaction up front and can return `BUSY`; read-to-write upgrades can fail. Commit errors do not uniformly imply the whole transaction was rolled back; inspect transaction state and handle rollback explicitly. [Official transaction semantics](https://sqlite.org/lang_transaction.html)
- Import already hash-checks snapshots, deterministically rebases colliding project IDs and retains old files after commit/marker publication. Preserve that resumability rather than rewriting it as uncontrolled dual-write. [store_import.c](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/src/app/store_import.c)
- Current file save and revision History append are separate operations; current backup exports SQL, copies manuscript files, and explicitly does not claim a single files-plus-database snapshot. Engine-local ACID cannot cover externally edited manuscript files. [Architecture §§5,10](https://github.com/anjaustin/scribodo/blob/69b98abf1ecf86c560b435a209327175c182eab1/docs/ARCHITECTURE.md)

### Inferences

**Required design, regardless of engine**

1. **Transactions and jobs:** domain row + source identity/hash + ingestion cursor + outbox intent commit together. Use a unique logical operation key. Claim in a short write transaction, commit before embedding/model/filesystem work, then ack only if owner/fence/generation still match. Expired claims are retryable; external effects are at-least-once and must be idempotent. “Exactly once” cannot span SQL and an external vector index merely by choosing SQLite.
2. **SQLite-specific port:** replace `SELECT ... FOR UPDATE` with short `BEGIN IMMEDIATE`/conditional updates; rewrite upsert/update-join/timestamps/full-text SQL deliberately; use integer UTC timestamps if needed for precision; retain generation and fence checks even with a single in-process worker. Keep expensive hashing/model calls outside write transactions. Never use `INSERT OR REPLACE` as a casual equivalent of MariaDB upsert because replacement can have delete/reinsert effects.
3. **Connections/deadlines:** thread-owned connections remain reasonable; alternatively one bounded writer queue plus read connections. No busy loops or SQL disk work on rendering thread. Verify `foreign_keys=ON`, actual WAL mode, sync/fullfsync policy on connections; prepare/finalize discipline so long readers do not pin WAL. Keep cancellation/timeout paths; a server socket timeout disappearing does not mean filesystem I/O is always bounded.
4. **Migration:** read a consistent MariaDB export into a new SQLite DB; record schema version + migration checksums and run applicable SQLite DDL/data changes transactionally. Compare every original source byte/hash, ID, sequence, version, consent/authority flag, saved pointer, source range, tombstone and job state. Fail closed on unsupported schema; retain original DB and export until independent restore acceptance. Publish authority marker only after validation and durable commit; no automatic failback into a competing history.
5. **File/DB reconciliation:** give each save operation a durable intent containing document/revision IDs, expected old identity/hash and exact proposed bytes/hash; atomically replace file, then finalize saved-revision pointer. On restart, compare actual bytes with old/new expected states; finalize matching new state or preserve/report conflict, never blindly replay over an externally changed manuscript. This is an application journal/reconciliation protocol, not a cross-resource SQLite transaction. Preserve unsaved accepted-edit revisions as unsaved.
6. **Backup:** briefly quiesce app-owned mutations/drain save intents if claiming one application cut; stage SQL snapshot plus independent files, verify each against the snapshot’s saved identities, detect external edits and retry or disclose mismatch. Publish complete manifest only after all pieces are verified/durable. Restore into a fresh folder, validate before import, explicitly reidentity forks, never auto-overwrite current authority. Qdrant stays disposable/rebuildable across whichever retrieval backend the other researcher selects.

**Falsifiable adoption gates**

- **SQLite gate:** a separate throwaway backend prototype imports one exported project with long/unicode/sanitization-colliding names, chats, revisions, notes/canon/findings/source ranges, memory consent and pending jobs. Assert byte-for-byte/ID-for-ID equivalence; run the existing DB, UI-store, import/copy/move, crash and backup/restore contracts plus all three audit regressions. Zero silent loss, cross-document source resolution or duplicate logical append tolerated.
- **Concurrency/durability gate:** simultaneous chat append, observer publication, import, Recall reader, outbox delivery and online backup; kill before/after SQL commit, file rename, marker publication, index success and ack. Inject disk-full/I/O/permission errors and stale workers. Require bounded UI work and no job starvation or unbounded WAL. Measure p50/p95/p99 plus worst-case UI stalls with FULL + fullfsync, not only relaxed durability.
- **Operational simplification gate:** compare app + MariaDB + helper/daemon processes versus app + SQLite under the same workload, reporting peak total RSS/PSS where available, cold-open, disk writes, backup size/time, recovery time, linked deps and first-party operational modules actually deletable. If critical import/backup loses liveness because the single writer is saturated, or the migration keeps all old backends indefinitely, the simplification case fails.
- **libarchive gate:** build restricted ARM64 feature set, capture exact transitive dependency/license inventory; malicious path/symlink/hardlink/special-file, expanded-size, corrupt/truncated archive tests; restore into fresh directory and compare bytes/metadata. Integrate only if it removes meaningful helper/process code without expanding accepted formats unnecessarily.
- **Git gate (only if demanded):** compare SQL full snapshots against libgit2 blob/commit storage on realistic repeated manuscript edits, measuring total bytes after packing, CPU/RSS, read/restore latency, crash recovery and required coordination code. Reject if benefit is merely “Git has history” while SQL still must preserve every semantic revision and source pointer.
- **restic gate (optional):** fully offline external-disk repository; restore on a clean machine from staged completed bundles after simulated source-drive loss; test forgotten/wrong key and damaged repository disclosure, retention/prune safety and user recovery instructions. No service/network requirement may leak into normal writing.

### Gaps

- These are proposed gates, **not executed results**. Repository’s prior green tests do not prove a new backend preserves semantics, and current audit defects remain open.
- No source-supported numeric adoption threshold for latency/memory is available; coordinator should use Scribodo’s existing UI/scale budgets, establish baseline and precommit thresholds before running the prototype.
