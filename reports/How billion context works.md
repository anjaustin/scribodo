# How billion context works

**Executive conclusion.** `ranxianglei/billion-context` provides functional, long-session memory by replacing selected old exchanges with independently anchored summaries, later distilling selected summaries, retaining addressable source material outside the prompt, and orchestrating retrieval and further inference within a bounded working window. Its important contribution is this coordinated lifecycle—not one continuously rewritten recap or a larger model window. **The kernel manages identity, coverage, protection and rendering; models write summaries; the proxy executes tools and continuations; storage makes recovery possible.** At the inspected snapshot, aging does not automatically merge blocks, exposed search is lexical, and restoration depends on which originals the host actually retained. Reported results support the feasibility of sustained sessions and coherent conversational memory, but show substantial exact-retrieval losses and do not establish small-model fiction-memory quality. For Scribodo, the strongest adaptation hypothesis is a host-scheduled, source-linked memory planner using MariaDB authority, bounded source retrieval and paged host history; recursive tiers and upstream reuse should earn their complexity through matched local experiments. The objective remains uninterrupted writing without repeatedly re-explaining the book, with **GAP-003 whole-manuscript scale and sustained use as P0**, not implementation approval or a reopening of the four deferred gaps.

**Scope and evidence.** Source semantics throughout are pinned to **`c3dfbe6b21a1b2fc3642594043bc81fd2ae91247`**, root package **0.1.212**, embedded `acp-kernel` **0.0.182**. The repository-hosted benchmark evaluates **0.1.202**; the living paper includes an older “v0.1” pilot and observational production evidence. Those are separate evidence populations. This synthesis builds on all four [research notes](../research_notes/How%20billion%20context%20works/) and treats [MEMORY-001](../docs/MEMORY-001-long-lived-context.md) as preliminary hypotheses. Researchers inspected source, documents and test assertions: **no dependency was installed or executed, and no upstream tests or model experiments were run**. Scribodo observations describe the researchers’ local checkout, recorded as `3e7add862226e61abf34629bd973c3123b94ac18` plus planning files, not remotely pinned upstream artifacts. ([Package](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/package.json#L1-L5); [kernel package](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/package.json#L1-L5))

## Independent summaries form an addressable coverage graph

### Four responsibilities must cooperate

The host-independent kernel is a TypeScript library, not a memory server or summarization model. `processTurn()` transforms supplied messages and state into a folded view, recommendations and status signals. `applyCompression()` validates supplied summary strings and changes coverage state; it does not invoke inference or persist anything. The proxy supplies session identity, wire conversion, tool exposure, model requests and persistence. A normal conversation model writes summaries in its `compress` arguments; a separately configured summarizer is optional. Original retention belongs to the surrounding host/storage machinery, not to the block IDs themselves. ([Kernel inputs and outputs](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L76-L151); [pipeline](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L930-L1008))

```text
Host transcript / native tools / author UI
             | request + stable session/history identity
             v
Proxy / adapter: src/server/handle.ts -> prepareOpenai()
             | openaiToCore(); keep originalMessages
             v
Kernel: processTurn() -> syncBlocks -> prune -> recommend/nudge
             | bounded folded messages + refs + tool schemas
             v
Conversation model ---------------- Optional summary service
             | compress(ranges, summary)       | authored summaries
             v                                v
Proxy: runCompressLoop() -> executeProxyToolAsync()
       -> applyConfiguredCompression() -> applyRanges()
             |
Kernel: applyCompression() -> projectUnit() -> new block/coverage
             |
Proxy: capture originals; refreshFolded(); continue inference
             |
Storage: src/persist.ts + src/storage/store.ts
         transcript/CAS + block state/views + optional CCR store
             ^
             | search_context / decompress / optional acp_retrieve
```

This diagram describes the ordinary OpenAI streaming proxy path, not every adapter’s wire shape. `handle.ts` prepares, preflights and forwards; `src/loop/core.ts` owns internal continuation. Native plugin mode changes ownership: the host registers schemas from `/__bili/plugin/manifest`, executes tools through `/__bili/plugin/tool`, and runs its native tool loop. **Current preparation can supply nudges in both modes**; the blanket claim that plugins suppress all nudges is stale. ([Ingress](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/handle.ts#L2852-L2920); [plugin contract](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/plugin.ts#L92-L126); [current nudge injection](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/prepare-openai.ts#L442-L447))

### Coverage records what a summary replaces, not its truth

`CoreMessage` projects role, content type, text, tool-call identity and optional thinking-token mass, checkpoint marker, stable `ledgerSeq` and timestamp. It is not complete provider wire JSON. Model-visible `m00001` references alias raw message IDs; `b1` identifies a block and `r1` a compression run. Refs remain stable and sparse, widen beyond five digits, and have a finite ceiling of **9,999,999**. `BLOCKED` is a protection sentinel, not reusable message identity. Database sequence numbers and content hashes have different purposes: order/occurrence versus content identity. ([Types](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/types.ts#L1-L115); [refs](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/refs.ts#L1-L145))

A `CompressionBlock` contains its summary/topic, tier, direct and effective message IDs, child block IDs, input-token mass, creation time, survival count, generation and active state, plus restoration/origin metadata. **Direct coverage** consists of newly folded message IDs not covered by an active block before the apply call. **Effective coverage** includes inherited child coverage as well. `directBlockIds` preserves the ancestry graph. Consumed children become inactive, not deleted; active blocks define the current summary frontier that hides originals. An exact ledger interval is recorded only when all constituents prove one contiguous interval; otherwise ID membership remains the evidence. These arrays contain identities, not original bodies. ([Projection](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/unit-projection.ts#L206-L250); [block creation and intervals](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L1841-L1931))

Tier and generation are independent. Plain message-endpoint folds output **T1**, incorporating nested T1 blocks without necessarily promoting them. If either endpoint is a block ref, the operation consumes nested active blocks at the **minimum nested tier**, and outputs `min(3, tier + 1)`. Mixed-tier spans therefore do not simply merge everything; T3 can be rewritten into another T3. `advanceSurvival()` marks active blocks `old` after five sync passes, which need not equal five user turns. **No age-triggered merge node exists in this snapshot.** `kernel/DESIGN.md`’s `merge-blocks`/`Config.merge` account and README merge exports disagree with the actual pipeline. This is a coverage graph with a compact active frontier, not an enforced balanced tree or demonstrated logarithmic algorithm. ([Tier selection](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/unit-projection.ts#L206-L232); [age update](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/state.ts#L89-L100); [actual pipeline](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L1069-L1095); [stale design](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/DESIGN.md#L90-L121))

Protection is also structural. Defaults preserve three recent eligible visible messages, a 5,000-token recent window and the latest real user anchor, with tool-pair closure. Separate hard exclusions cover configured tools/paths, latest-only instances, metadata/control payloads and unrecoverable media. The newest three successful compress exchanges receive special protection; older exchanges become foldable, while persistent `acp_rule` records remain protected. Recoverable media handles are mechanically carried into summaries; unavailable media cannot be made recoverable by prompting. Shared `projectUnit()` screens both recommendations and actual execution against the appropriate source view, widens ordinary boundaries for tool/reasoning integrity and removes protected IDs from effective coverage too. Otherwise a supposedly protected original could disappear through inherited pruning. ([Recent protection](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/recommend.ts#L65-L197); [hard protection](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/protected.ts#L18-L130); [projection and integrity](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/unit-projection.ts#L234-L503))

## Compression changes the next inference through explicit tool execution

### A constructed session shows folding and recovery

Consider a book-development chat whose old messages `m00002..m00020` discuss a ferry scene, including the exact phrase “cobalt heron 17.” **All counts and events in this example are illustrative, not measured or executed.** Suppose the current rendered request is 26K tokens against an effective 32K input allowance, with 10K eligible old tokens and a protected recent tail. Pressure can recommend folding, subject to the benefit floor. The conversation model submits `compress` with endpoints, topic and a summary of at least 50 trimmed characters; assume the source exceeds the 5,000-character gate and no integrity conflicts exist. `applyCompression()` creates `b1:T1`, and the proxy captures available source renderings. A 10K-token source becoming a 700-token summary would reduce the represented text substantially, but the actual final request must be recounted with wrappers and tools. The kernel’s `compressedTokens` records **input mass**, not net savings. ([Apply path](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L1702-L1880); [source capture](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/stream.ts#L1297-L1333))

The next render hides covered originals and inserts `b1` at its history anchor. If the exact originating compress call is already visible, its summary arguments can carry the representation instead, avoiding duplicate synthetic text; when that carrier disappears, the synthetic summary returns. Ordinary proxy mode’s internal call is ephemeral, so an anchored `acp_summary` must persist in the outbound view. `prepareOpenai()` revoices those generated system-role carriers as user messages without moving them to the head. **The host normally retains its original transcript**, while the person sees an ACP progress marker and the eventual answer, not the internal compress frames. ([Pruning/carriers](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/prune.ts#L134-L310); [wire rendering](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/prepare-openai.ts#L404-L447))

Later `m00021..m00040` becomes independent `b2:T1`; `b1` remains unchanged. Submitting `b1..b2` against the pruned view creates `b3:T2`, with children `[b1,b2]` and inherited effective coverage; direct message IDs can be empty. The child summaries remain stored but inactive. Further T2 blocks can become T3, and T3 can be condensed again. Aging alone never initiates these changes. Assume the ferry summary preserved the topic but omitted the phrase. A later request asking for the ferry’s code gives the model a reason to call `search_context`, inspect a block hit, then `decompress({blockId:"b1",full:true})`. **The phrase comes from retained original text, not inversion of the higher-level summary.** If nothing retained it, decompression can fall back to a summary and cannot recover the missing phrase. ([Post-prune promotion assertions, inspected only](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/tests/regression-promote-after-prune.test.ts#L82-L150); [restore fallback](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/decompress-shared.ts#L147-L247))

The proxy inserts paired tool calls/results internally, refreshes folded history after a successful fold, and requests continuation. A whole-block inline restore leaves its block active, marking `restoredInline` so restored material can be refolded; it does not permanently replace the frontier with the complete historical transcript. Default decompression is **one level**, meaning direct messages plus child summaries; `full:true` requests the cached original-message rendering. A file export restores text to a file, not automatically to the model’s attention: the host must be able to read that path. The following is abbreviated control flow, not executable upstream code. ([Refresh and pairing](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/loop/core.ts#L1402-L1515); [relay refresh](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/relay.ts#L2170-L2227))

```text
prepareOpenai(history, session):
    originals = openaiToCore(history)
    folded, state, nudge = processTurn(originals, state)
    return render(folded, static_instructions, tools, trailing_nudge)

model emits compress(specs):
    summaries = specs.summary                 # default: main-model authored
    state, result = applyCompression(originals, state, specs)
    capture_available_originals(result)
    folded = processTurn(originals, state)     # realize new active coverage
    continue_model(folded, paired_tool_receipt)
```

### Defaults encourage compression; preflight enforces fit separately

**A nudge is advisory**, not forced summary execution. The default main model both selects endpoints and writes the summaries; the kernel merely recommends legal ranges and a tier. Important defaults and units are below; host overrides and reachability/circuit-breaker gates still apply. ([Kernel defaults](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/config.ts#L3-L70); [selection formulas](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L1978-L2307))

| Mechanism | Pinned default and meaning |
|---|---|
| Growth step | `G=min(cap,max(floor,round(limit×ratio)))`; ratio .05, floor=cap=50,000, so G=50,000 |
| Growth eligibility | `F=max(20,000,.45×G)=22,500`; ready mass T1=50K, T2/T3=75K; not a periodic “every 50K” timer |
| Pressure | At ≥75%, bypass growth/cadence and choose enabled tier with greatest eligible mass, requiring `max(5,000,1%×limit)` benefit unless overridden |
| First-sight backlog | ≥45% usage with qualifying mass can bypass normal growth; 45% is not a universal lower nudge bound |
| Tier count signals | 1,000 active T1 / 2,000 active T2; count signals are recommendations, not prerequisites for explicit promotion |
| Range/summary gates | Batch raw range ≥5,000 **characters** unless exempt; trimmed summary 50–20,000 **characters**, with per-spec maximum override |
| Optional lanes | CCR, absorb and crush off; experimental fold-point carrier relocation off |

Outside pressure, normal selection prefers T1, with tier-specific readiness and cadence for higher tiers. A T1 response harvesting under half the offered mass can set `t1HarvestStall`, allowing qualified distillation ahead of repeatedly unproductive T1 work. Defaults also include nudge frequency 5, iteration threshold 15 and soft force, but these are not a universal five-turn schedule. Tier-writing targets such as T2’s 50–150 tokens per source block and T3’s 30–60 are **prompt instructions, not validator-enforced semantic or token guarantees**. Kernel validation does not prove truth, quote fidelity or even net shrink; preflight adds its own non-shrinking-summary rejection using a 1.05 shrink tolerance. ([Harvest logic](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L867-L890); [summary rules](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compression-rules.ts#L38-L145); [preflight shrink policy](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/preflight.ts#L92-L106))

`applyCompression()` clones state, resolves endpoints, screens ranges and validates summaries before publishing blocks. Overlapping batch ranges are skipped, earliest spatial range winning. A candidate summary-length failure rejects the candidate batch; an apply-level exception rolls back sibling folds. **Unknown/invalid references are per-range errors and can coexist with successful siblings**, while consumed/protected work can acknowledge a no-op. Thus “fully atomic compression calls” overstates the contract. The API returns state/results, not a pruned message array; subsequent `processTurn()` realizes the new view. ([Classification, gates and rollback](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L453-L927))

Streaming requires more than stripping a tool name. The OpenAI adapter buffers fragmented names/arguments, hides the four core proxy tools, forwards genuine host-tool frames, and removes premature finish signals across upstream continuations. Internal re-request occurs only when proxy results exist **and no real host calls exist**; mixed compress-plus-host-tool rounds return control to the host. The cap is **10 loop rounds**, ending with `length` if exhausted. A static-analysis concern remains: the adapter’s private-tool classifier omits optional CCR `acp_retrieve`/dynamic names even though the dispatcher recognizes them. That is an **unresolved optional-mode integration risk**, not an exercised failure, confirmed vulnerability or defect established in default four-tool operation. ([Streaming classifier](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/loop/adapter-openai.ts#L376-L454); [dispatch and loop bound](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/loop/core.ts#L1519-L1562))

Preflight runs **before forwarding** when the prepared payload reaches its effective target. It nominates ranges programmatically, prioritizes largest payoff outside recent protection, can relax soft recent protection to zero, and makes dedicated summary calls—even when using the same main model/provider. Source chunks use a .6 summary-window fraction with a 2,000-token minimum; ordinary summary output starts capped at 32,768 tokens and is clamped to known model/window limits. Base depth and summary-call budgets are 16, scaling to 32 with overshoot; protection relaxation can reset call/retry accounting, and separate tier rescue permits six calls of at most 60,000 source characters. Transient empties permit two same-span retries within four wasted retries per protection regime. These component caps **do not create one total turn deadline or universal maximum of 16 HTTP calls**. ([Preflight constants](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/preflight.ts#L55-L139); [scaled budgets](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/preflight.ts#L1837-L1867); [range ordering](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/preflight.ts#L2375-L2418))

Optional external summarization previews the entire batch’s protection, sends selected source plus read-only task/summary reference material to configured targets, and commits generated summaries rather than the conversation model’s hints. Changed revisions/cancellation reject stale publication; successful ranges can produce an explicit partial-success receipt. Defaults are concurrency **4**, **50 seconds per batch**, **25 seconds per target**, **64 KiB summary bytes**, with queue time charged; each `summarize()` invocation receives a fresh batch budget. Invalid enabled settings fail rather than silently using main-model summaries. Optional external `autoFold:true` targets half the effective window subject to floor/overflow constraints, with a ten-minute failure backoff. Optional model-decided nudge timing is a separate 200-output-token, 15-second decision call—not summarization. ([External commit](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/external-summary-compress.ts#L51-L138); [executor](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/external-summary.ts#L234-L306); [auto-fold](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/external-summary-surface.ts#L68-L152); [decision defaults](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/nudge-decide.ts#L24-L43))

Emergency paths are deliberately different. At ≥95% reported usage, kernel truncation targets `threshold×limit×.9`, ordinarily **85.5%**: first clip largest qualifying tool results, then older user/assistant prose, retaining approximately 2,000 prefix and suffix characters. Candidates are ≥1,000 tokens outside the newest N array messages. This does **not** consult all normal fold-protection machinery; system text, synthetic summaries, retrieved injections and call arguments are excluded, but an older protected user/tool body can be clipped. Up to 64 ref-keyed clips latch until a successful fold resets them; three consecutive hot, nonproductive events can return `terminalEscape`. Separately, preflight overshoot **>19.2×** switches to structural digests, zero summary inference and at most 512 CPU-only rounds—not equivalent semantic summaries. ([Clipping/terminal path](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/compress.ts#L1531-L1672); [candidate exclusions](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/truncate-tools.ts#L29-L149); [digest trigger](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/preflight.ts#L148-L168))

The generic window fallback is 200K, not discovery of an unknown local model’s capacity. Character token heuristics, route-calibrated usage and explicit overhead reserves drive fit decisions. Default output headroom is `W−min(maxOutput,.25W)` when applicable. Recognized overflow can trigger one same-request refold/resend; failure remains possible. After a 30-second hold has committed HTTP 200, later errors must be in-band. **A completed stream or small final prompt does not prove a completed user task.** ([Headroom](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/util.ts#L565-L600); [estimates](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/tokenize.ts#L5-L40); [overflow retry](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/relay.ts#L1350-L1497); [in-band failures](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/handle.ts#L2880-L2917))

Final egress has a separate `clampOutgoingOutput()`/`clampOutputBudget()` policy on OpenAI, Responses and Google paths, not a universal Anthropic-wire clamp. It first tries an input estimate inflated by 1.12, subtracts `max(2,048,ceil(.05×estimate))` margin, and respects a known output ceiling. Reductions retain a 4,096-token capability floor bounded by raw remaining headroom; if the computed cap is below 1,024, the clamp declines rather than starving a terminal turn. It can retry calculation on the uninflated estimate. This is estimate-based protection, not backend-tokenizer proof of fit, and wrapper Anthropic routes can depend on overflow recovery instead. ([Clamp constants and wire scope](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/budget.ts#L12-L44); [exact clamp](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/budget.ts#L300-L337))

## Retained originals and stable prefixes help, but do not bound everything

### Recall depends on clues, searchable scope and retained bodies

The archive is several objects, not one magical transcript. Unified storage records first-seen messages by session/sequence with message-ID/content-hash uniqueness, SHA-256-addressed bodies, pointer-based live views and block payloads. `Session.blockContents` caches `one` and `full` rendered text; these are not necessarily original wire JSON or all multimodal bytes. Optional `MessageContentStore` for CCR separately deduplicates original text by hash and binds refs to metadata. Default persistence is enabled, unified mode `full`, backend SQLite, JSON envelope writer on; optional encryption disables the cleartext unified sidecar. MySQL 8.0 has an implemented async backend, but that does not establish drop-in compatibility with Scribodo’s MariaDB authority/schema. ([Schema](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/storage/schema.ts#L123-L188); [block caches](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/session.ts#L17-L82); [backend/defaults](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/storage/backend.ts#L337-L414); [storage knobs](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/knobs.ts#L841-L897))

`executeSearchContext()` searches topic+summary across **active and inactive** blocks using explicit `algorithm:"substring"`: lowercase, whitespace-split terms, summed literal occurrence counts, OR-like matching, no stemming, typo tolerance or vector search. Default limit is five summary hits. A resident session can additionally search cached `full.text`, strip ACP chrome and return up to the limit in distinct original-only hits. It does not automatically search every raw-ledger or CCR row. Errors degrade to summary-only search. A disk-only foreign session resolves state without its originals provider, so that path is **summary-only**; ancestor fallback, capped at eight hops, first needs a summary lexical match. The kernel’s other search APIs do not change what this exposed tool actually invokes. ([Search dispatch/corpora](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/decompress-shared.ts#L791-L995); [literal scoring](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/search/algorithms/substring.ts#L4-L32))

Whole-block `decompress` uses cached one/full content, then available-message collection, then summary fallback; native-compaction-archived blocks can be explicitly non-restorable. Message-subrange decompression requires CCR enabled and surviving per-message source coverage, with missing parts skippable. CCR itself defaults off: arrival-time large eligible tool text, ordinarily ≥4,000 estimated tokens, becomes a deterministic ref/size/head placeholder while originals remain stored. Fold-time capture can retain covered text, excluding reasoning/placeholders. `acp_retrieve` is exact ref→hash→text lookup, not search; sufficiently large results normally become proxy-local export pointers when an export directory is supplied. File-write failures return failure and a bounded preview. ([Decompression](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/decompress-shared.ts#L147-L247); [range restoration](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/decompress-shared.ts#L379-L480); [CCR retrieval/capture](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/ccr.ts#L395-L658); [export delivery](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/store.ts#L199-L245))

**Storage reversibility is not behavioral recall.** An omitted clue can prevent the model from knowing that it needs retrieval at all. Synonyms without shared substrings, generic words swamping a limited hit list, cold-session restrictions, absent source captures or reset refs can then block recovery despite some retained bytes. The architecture supplies a repair route, not an omniscient trigger. For book memory, persistent objectives, entity aliases, correction lineage and uncertainty deserve explicit derived records and evaluated retrieval policies rather than faith that increasingly condensed prose will always preserve the retrieval cue.

### Cache stability reduces repeated work only when the backend cooperates

Static instructions and consistent tool schemas stay at the head; changing nudges/status sit at the tail. Independent summaries remain byte-stable until touched, and internal refresh aims to match the next host replay exactly. A fold nevertheless changes tokens from its earliest rewritten anchor onward; an older tier merge can move that invalidation backward. Carrier changes, separators, ephemeral loop records, tools, model/thinking parameters, route or credentials can also change cache reuse. Inspected mock-upstream regressions assert prefix equality and post-fold representation persistence, **not real provider cache hits, GPU time or bills**. Proxy-owned cache-key stamping is disabled by default at this snapshot. ([Stable preparation](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/prepare-openai.ts#L411-L447); [prefix assertions](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/tests/cache-friendly-proxy.test.ts#L128-L172); [cache-key handling](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/server/prepare-openai.ts#L538-L561))

Compression therefore is not free: summary generation, retries, continuation, retrieval and fold-time reprocessing must be amortized against subsequent savings. Provider discounted cached-input prices are not measurements of proportional compute reduction. Scribodo’s [existing LFM3 runtime report](../docs/MODEL-001-lfm3-runtime.md#performance-llamacpp-bf16-kv-m4) describes partial recurrent/sliding-window snapshot reuse: even an identical 6,390-token prompt reprocessed 516 tokens in that earlier local measurement. No researcher reran it here. Stable prefixes are useful, but remote cache-share claims cannot be transferred to LFM3. Also, Scribodo currently prepends attachments to the **newest user message**, despite a stable-prefix comment; stability should be established from rendered requests, not inferred from that comment. ([Local construction](../src/llm/chat.c))

### Prompt bounds, resident bounds and archive growth are separate

Warm-cache controls default to 256 resident sessions, zero boot warming, an optional 64 MiB decoded warm budget and a 512 MiB pooled estimated resident budget. Persisted folded tails default to 16,384 tokens, retaining at least one whole message even if oversized. Successful settled saves permit idle raw-tail shedding and lazy originals/metadata/CCR. But hot block/ref state is not droppable, so the per-session “hard” budget is **not a process-RSS ceiling**. `LazyBlockContents.get()` rematerializes the whole session map. Search scans retained block texts; feature caching is capped by eight million source characters, not exact bytes. Paged database reads bound query batches, not final live metadata. No demonstrated constant whole-system per-turn cost follows. ([Residency knobs](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/knobs.ts#L402-L457); [lazy map](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/session.ts#L31-L82); [folded tail](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/persist.ts#L4061-L4090); [search cache](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/kernel/src/search/doc-cache.ts#L1-L85))

Archive/disk growth remains real. Absent historical text rows can be retired rather than deleted; media references have different retirement behavior. Inactive blocks, coverage arrays and nested full renderings consume space, with possible duplicated rendered content across tiers. Legacy deletion GC defaults off. Unified archive age defaults to 365 days but inspected entry points are explicit CLI/admin maintenance, not an established automatic timer. Cold archival writes to a shared JSONL log; restoration reads/splits and rewrites that whole log. Transactional ingestion and rename-based saves help, but 500 ms debounced JSON writes lack file/directory fsync, and JSON/CCR/DB/archive operations are not one cross-file transaction. ([Retirement](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/storage/store.ts#L923-L967); [archive/restore](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/storage/store.ts#L1859-L2040); [save contract](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/src/persist.ts#L60-L100))

The host can dominate even when the model request is small. **Issue #5796** reports DSH 0.2.1-rc.3/bili 0.1.212, reporter build `daa082ea` rather than this inspected commit: about 29,619 host messages, 51.2 MiB full resends and 11.26M host-message tokens, versus approximately 63K forwarded tokens and seven active/567 total blocks. Reported medians were roughly 27 seconds host build/upload and 5.97 seconds ingest. This is mutable user-reported evidence, locally captured with update time `2026-11-06T12:45:45Z`, not independently reproduced timing. It illustrates why host all-history copies, serialization and UI caches must be addressed directly. Inspected 320-file storage and 6 MiB restart regressions are narrow synthetic designs, not billion-token factual-recall trials; restart assertions allow a 500 ms settle before kill. ([Issue](https://github.com/ranxianglei/billion-context/issues/5796); [storage test](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/tests/bounded-storage-scale.test.ts#L10-L47); [restart fixture](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/tests/issue5631-restart-survival.test.ts#L68-L81))

## Published evidence supports continuity, not uniform recall or automatic reuse

The pinned paper reports **18.76B cumulative input tokens** on its main host: 1.75B fresh plus 17.01B cache reads, approximately 24.7B across differing three-host observation windows. The leading OpenCode session reports 12,049 calls and about 1.52B cumulative input with a roughly 126K mean prompt. Repeated input/cache reading counts repeatedly; this is not unique archive size or successful remembered facts. That session’s 6.45M compressed-token statistic is another unit, and kernel input-mass counters are not guaranteed unique/net savings. The paper’s **28.6B/106-day** capacity is a fitted simulation at a 1M window, about 19× beyond its largest observed session, with unobserved/design-assumed T3 behavior. Reported 94.2% short-gap cache share is provider token telemetry, not local speed or recall. ([Paper §§5–7](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/paper/model-driven-incremental-hierarchical-compression-training-free-multi-generational-context-management-for-long-lived-coding-agents.md))

The repository-hosted report describes itself as an independent third-party, 1,500-instance evaluation of **v0.1.202**, using **DeepSeek V4.1 Flash 1017**, **Qwen3-Embedding-8B**, **Qwen3-Reranker-4B** and **Pi CLI 0.73.1**. Its task split matters more than one headline. ([Benchmark setup/results](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/benchmarks/third-party-1500/README.md))

| Reported task | Compression versus comparison | Interpretation |
|---|---|---|
| LongMemEval-S overall | 79.20% vs full 83.20%, best retrieval 62.60% | Coherent retained state beats these retrieval arms, but not full context overall |
| LME multi-session reasoning | 79.70% vs reranked retrieval 45.11% | Meaningful support for conversational continuity |
| ContextBench utilized-span F1 | .3097 vs full .2928 | Code-span localization, not fiction-writing quality; evidence recall slightly trails full |
| MAB verbatim needle | **27% exact match vs full 69%, BM25 59%, reranked 66.33%** | Exact detail is a major weakness; some failures also involve empty final content after reasoning answers |
| MAB recommendation, 1.48M-token histories | 199/199 completed, Recall@10 18.58% vs BM25 22.08% | “100% survival” means avoiding overflow failures, not remembering everything |
| MAB BookSum | ROUGE-L F1 38.62% vs full 42.65% | No established superiority for book summarization |

Cost comparisons require matching price assumptions and cache reuse. LME’s observed full-context bill is **$0.42 versus compression $2.30**, with 98.1% full-context prefix reuse across shared haystacks. The promoted $7.97 full versus $2.30 compression uses a modeled independent-session accounting assumption, not that observed bill. The MAB “30×” ratio uses 1.48M divided by 49.5K **mean** prompt, not the approximately 16K steady-state figure. Neither provider prices nor the benchmark’s larger embedding/reranking stack transfers to the M4. ([Benchmark §§2–5](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/benchmarks/third-party-1500/README.md))

The paper’s older Qwen3.8-27B/sGLang temperature-zero pilot reports 31–54% fewer billed tokens in controlled workloads, but sliding-window truncation and threshold compaction did not activate at the main workload point, and no controlled run exercised T2+. A zero-compression doctrine/ref-tag control reproduced almost all headline re-fetch improvement, **62% versus 63%**. Restoration succeeded 6/6 when instructed but **spontaneous adoption was zero**. Fixed-cadence summaries were cheaper on repetitive work, conservative folding outperformed aggressive folding on phase-structured probes, and repeated probes risk feeding answers back into history. At 16K, the roughly 2K-token doctrine was reported as about 25% fixed per-call overhead in that workload. These are reasons to isolate mechanisms and measure local overhead, not reject summaries wholesale. ([Paper §8.1](https://github.com/ranxianglei/billion-context/blob/c3dfbe6b21a1b2fc3642594043bc81fd2ae91247/paper/model-driven-incremental-hierarchical-compression-training-free-multi-generational-context-management-for-long-lived-coding-agents.md))

**Independent reproducibility was not established.** The benchmark directory contains reports/charts, not a disclosed executable harness, per-item predictions, evaluator identity, dates/seeds, judge prompts or confidence intervals. The paper says production stores, sanitized corpus and experiment workspace/harness are not yet public; plotting source references missing data and author-local paths. Its author-verified/analytical/planned labels are not external verification, and observational production telemetry cannot establish task quality. The cited Full Cost Attribution paper concerns Paritok, not independent validation of billion-context. No controlled multi-tier semantic-drift curve, 1.7B-model evaluation or authority-aware fiction-memory trial was available in the inspected evidence. ## Scribodo should test bounded host memory before choosing tiers or reuse

### Preserve authority while bounding the whole application

Scribodo already owns its inference path and durable project records. **MariaDB remains authoritative; Qdrant remains a rebuildable derived index**, not a second source of canon. A memory brief must retain immutable source IDs/revisions/hashes, coverage, summarizer/prompt version, scope, validity and permissions. It must distinguish story time from discussion/revision time, author-approved correction from character belief, and speculative alternatives from canon. Observer findings stay outside creative memory unless explicitly brought through **Discuss**. Retrieved prose is untrusted reference data, never a new instruction or authority to edit the manuscript. Source deletion, retraction, revision or scope change must invalidate dependent briefs and ancestors; stale background work cannot publish against a newer source version. ([Product authority](../docs/SOW.md); [semantic API](../src/llm/semantic.h))

Remote eligibility must derive from **all underlying sources**, including read-only summarizer reference material—not the destination summary’s label. A local-only passage cannot become remotely eligible merely by being summarized, retrieved or followed by an explicit provider switch. No automatic remote fallback is authorized. Model serving remains the pinned **BF16 LFM3-1.7B on M4/16GB**, supervised through its private authenticated Unix socket, with `-fa off`, BF16 K/V, two slots and host prompt cache disabled. Use the actual memory-fitted per-slot context and real tokenizer/template, not the model’s advertised maximum or upstream’s anonymous 200K fallback. ([Runtime contract](../docs/MODEL-001-lfm3-runtime.md); [remote filtering/construction](../src/llm/chat.c))

Current `chat_build_request_ex()` reserves 1,024 reply tokens plus 256 margin, shares up to 60% of input allowance among attachments, and keeps newest fitting turns. Before calling the builder, the worker adjusts the effective `slot_ctx` budget for the author’s configured reply length in the sampling settings; the fixed 1,024-token reserve is a builder detail, **not a universal app reply cap**. Older data persists without a general creative-memory planner. More importantly for P0, the worker copies eligible prior content before bounded selection, the store loads matching history without LIMIT, and the UI retains message text/wrap caches and full-list work. These are **source-identified scaling candidates, not measured bottlenecks**. An adaptation must page history, cap text/layout caches and retrieved bytes, fetch selected source ranges rather than clone the archive, and schedule bounded derivative jobs. Host-side work is part of memory correctness: a book remembered only after a half-minute blocking copy does not meet uninterrupted writing. ([Request builder](../src/llm/chat.c); [history loading](../src/app/store_chats.c); [UI caches](../src/ui/chat_view.c); [P0 scope](../docs/PRODUCT-GAPS.md#gap-003--whole-manuscript-scale-and-sustained-use-p0))

| Adaptation | Reusable value | Unproven integration burden and current recommendation |
|---|---|---|
| Full proxy | Protocol adapters, tool loops, storage/recovery, diagnostics | Node sidecar, Unix-socket/auth bridge, streaming/cancellation, duplicated authority, network/update policy and doctrine overhead. Quarantined comparison only; no generic HTTPS interception needed |
| Kernel sidecar | Shared projection, refs, coverage/tier lifecycle, rendering | Versioned JS IPC/state, host persistence, source retrieval, summarization and policy still required. Credible comparison arm if reuse offsets RAM/packaging cost |
| Native conceptual equivalent | Incremental briefs, protected tail, exact-source recall, stable frontier | Own C implementation/invariants, invalidation and tests. Best first hypothesis for existing ownership, not a proven performance or quality winner |

This preserves the earlier native-first recommendation only as an engineering hypothesis. Start with host-scheduled first-tier briefs and exact/semantic retrieval; add recursive promotion only if measured need justifies it. Upstream’s 50K growth and 5K protection constants were not tuned for this runtime. A scheduler can avoid requiring the 1.7B creative model to autonomously select/legalize memory tools, but it cannot remove the need to test its summary fidelity. No upstream benchmark makes a larger summarizer, 8B embedder or 4B reranker an acceptable hidden prerequisite.

### A discriminating experiment should expose failure, not assume success

**Freeze a reproducible baseline first.** Record app and llama.cpp commits, GGUF/hash, BF16 flags, embedding artifact, template/tokenizer, generation settings/seeds, effective contexts and warm/cold cache conditions. Use private-free fixtures with exact ground truth: proposed representative projects of approximately 100K and 300K manuscript words, conversations at 100/1K/10K messages, then stress at 100K messages/1M words if earlier gates pass. These are proposed workloads, not claimed typical usage or measured capability. Include separate conversations, revisions and explicitly eligible attachments rather than silently granting project-wide memory. ([Existing evaluation hypothesis](../docs/MEMORY-001-long-lived-context.md#p0-execution-plan-and-decision-gates))

Compare matched arms: current recent-window baseline; baseline plus bounded lexical/exact and existing semantic retrieval; retrieval plus host-scheduled T1 briefs; the same with explicit hierarchical promotion; and matched single-summary compaction. An oracle-source-excerpt control separates memory-selection errors from inability to answer even with evidence. Keep source/output budgets and LFM3 identical, and cost a kernel-sidecar substitution separately if evaluated. Probe exact quotations, Unicode names/numbers, early rare facts, chronology, corrections/retractions, unresolved contradictions, brainstorming versus canon and genuinely unanswerable questions after 1/2/4/8/16 compressions. Force higher-tier folds instead of assuming ordinary workloads exercise them; compare summary-of-summary with regeneration from originals. Use fresh branches/one-shot probes to prevent probe answers becoming memory. Report source-supported correctness, exact match where appropriate, citation accuracy, abstention and wrong-current-fact rates separately by task.

The final rendered request must satisfy `instructions + request + protected edit passage + recent turns + selected briefs + exact evidence + tool/template overhead + output reserve + margin <= effective context`. Start proposed resource caps at 32 retrieval candidates, eight selected source excerpts/eight briefs, one retrieval round and 64 MiB combined history/UI caches, then vary them explicitly rather than letting quality fixes erase the bound. A roughly 2K-source-token summary batch is an initial scheduling experiment, not an established optimum. Run it locally at low priority, cancel/preempt for foreground writing and measure backlog. Test 8K/16K/32K contexts only where memory fitting permits. Include MariaDB, Qdrant, embedder and editor in whole-system memory pressure/swap measurements.

Instrument host preparation, database/page reads, retrieval, summary input/output, rejected attempts, invalidation/rebuilds, inference prefill/generation, TTFT, streaming gaps, input-to-paint, archive growth, and warm/cold/restart behavior. Count total work, not just final prompt tokens or a provider cache discount. At fixed active context, increase archive size and look for growth in per-turn copies/scans/residency. Candidate p95 ≤50 ms/p99 ≤100 ms UI targets and ≤10% foreground-latency regression against matched baseline are **proposals for agreement before tuning**, not accepted SLAs. Run hours-long writing/idle/resume/restart sequences under resource contention. This extends GAP-003 without pretending novel-scale throughput or summary quality has already been measured.

Authority/privacy tests must include wrong-project IDs, local-only history followed by remote selection, undisclosed observer findings, source prompt injection/special tokens, stale jobs, mid-summary edits/deletion, scope removal, Qdrant loss, MariaDB unavailability, socket authentication failure and offline cancellation/restart. Memory failures should surface as unavailable/partial evidence, not “nothing was said,” and must never promote a summary to canon or edit without author action. Detailed crash-certification work remains deferred GAP-004; these checks address the memory experiment’s failure boundaries, not completion of that broader gap.

The decision rule is to choose the **simplest arm** with meaningful paired continuity improvement and acceptable exact-detail/abstention results, while meeting predeclared resource and zero-tolerance authority/privacy gates. Publish per-task errors, multiple seeds and paired uncertainty estimates. If briefs do not beat retrieval-only, do not add them; if tiers add drift/cost without benefit, do not add tiers; if LFM3 cannot summarize reliably, do not silently change model or send the book remotely. Next questions are therefore concrete: which early-book facts need explicit cue/index preservation, how quickly summaries drift across forced folds, whether originals-based refresh pays for itself, whether local snapshot reuse survives actual fold placement, and which host pages/caches dominate after long accumulation. Upstream-specific open questions include cold-original indexing, complete capture across chosen modes, optional CCR streaming classification, shipped-artifact/offline behavior and license/provenance review. None has a measured answer from this research.

## Conclusion

For Scribodo, the decisive design shift is to make long-lived memory a **source-addressable host service with bounded working sets**, not an emergent property of whatever transcript happens to fit. Summary coverage should mean “these sources were represented,” never “every relevant fact survived”; retrieval should remain available independently of the summary’s wording, and the author should not have to manage session resets to keep access to the book.

The next authorized decision can be smaller than adopting billion-context: agree on the continuity tasks and complete host/resource budgets that distinguish successful indefinite writing from merely successful prompt compression. That experiment can validate a useful first-tier memory system, reject unnecessary hierarchy, or justify kernel reuse on evidence—without changing Scribodo’s model, data authority or privacy contract.
